## 一、排序原则

1. **阻塞性优先于可见性**：会让 agent 停住的组件（登录门、审批、提问）比"好看"的组件更早做——它们不出问题只是因为还没触发。
2. **数据已就绪的优先**：`useChat`、`inputActions`、`useSessionPendingInteraction`、`loadOlder` 由官方数据面提供且已在运行；只差视图的先做，需要自己造数据的（设置、作业、调度）后做。
3. **遮蔽即欠债**：你遮蔽了官方的哪些行，就欠下哪些组件。优先级按"官方原本替你做了多少"来排（对照见 [遮蔽对照表](04-遮蔽对照表.md)）。

## 二、组件清单（按开发顺序）

| 顺序 | 组件 | 作用（为什么必须 / 不做会怎样） | 对应官方原组件 | 数据来源 / 接口 | 验收标准 |
|---|---|---|---|---|---|
| **1** | **登录页（认证门）** | 产品形态要求"先登录再看工作台"。它决定首屏渲染分支，是所有后续组件的前置门；不做则无法上线给多人使用 | **无官方对应**：DSH 自带的 Web UI 没有登录页，`dsh web` 也没有用户体系 | 自建 auth store + 宿主同源路由（`ctx.webserver.register`，前缀如 `/qs-auth/*`）→ 转发给 `services/authority` | 未登录只渲染登录页；登录成功后自动进入工作台；票据失效（401）自动退回登录页；登出清空状态 |
| **2** | **外壳骨架 + session 座位** | 承载一切组件的容器：顶栏 / 左导航 / 主区 / 右栏 / 状态条 / 浮层；**同时声明 `scope:'session'` 座位**——没有它所有会话数据与 hook 都取不到 | `ui-layout`（`AppFrame` 及 `sidebar`/`main`/`rightbar`/`shell.overlay` 四个顶层槽的声明者）、`ui-theme`（`--dsw-*` 令牌） | 自建布局 store（`@deepseek-ai/dsh-client-store`，属 baseline 可直接 require） | 布局可折叠/可拖拽、刷新后状态保持；官方 UI 仍完全不出现 |
| **3** | **会话列表与切换** | 没有它就没有"上下文"。多会话是你的核心形态，也是左导航的主体 | `ui-sidebar`（会话/工作区导航区） | `useSessions`（root 作用域标准座席） | 切换会话后所有面板跟随；新建/重命名/删除可见 |
| **4** | **输入与发送（composer）** | 唯一驱动 agent 的入口。没有它工作台只是只读观察器 | `ui-conversation`（输入机与会话编排）、`ui-input-trigger`（`@` 引用触发，可选） | `inputActions` prop + `useInput` hook | 发送 / 取消 / 排队可用；中文 IME 组合期不误发 |
| **5** | **助手流式输出（最小转写）** | 唯一能"看到 agent 在工作"的窗口；不接等于黑盒 | `ui-chat`（assistant 节点渲染）、`ui-conversation`（会话骨架） | `useChat`（chat target 快照，assistant 节点） | 发送后能看到流式增量；热重载后会话不丢 |
| **6** | **审批呈现与回答** | **不做会让 agent 无限期等待**：Host 侧 waterfall 在等答复，而官方审批 UI 未被渲染 | `ui-approval`（ApprovalPanel + `conversation.composer` 链） | `useSessionPendingInteraction` → `kind === 'approval'` → `answer('allowed-once' \| 'rejected')` | 真触发一次需审批的工具并放行 → 工具继续执行 |
| **7** | **用户提问呈现与回答** | 同 6：`ask_user_question` 是 agent 主动索取信息的唯一通道，不接则阻塞 | `ui-user-questions` | `useSessionPendingInteraction` → `kind === 'question'` | 触发一次提问并回答 → agent 继续 |

> **顺序说明**：1 与 2 属于**同一交付批次**——登录页由外壳承载（`root` occupant 内做分支），所以两者要么一起做，要么 2 先落地、1 紧随。
> **6 与 7 常被排到"以后再补"，这是最危险的决定**：它们在演示阶段不出现，在真实使用中必现。请与 3/4/5 并列进本阶段。

## 三、登录页专项说明

### 3.1 流程

```
未登录 → root occupant 渲染登录视图（不渲染工作台树）
   ↓ 提交凭证（或 SSO 回调）
浏览器 → 宿主同源路由 /qs-auth/login → 宿主 → services/authority
   ↓ 校验通过
宿主下发票据（建议 httpOnly Cookie）→ 前端 auth store 置为已登录
   ↓
root 切换渲染工作台树（外壳 + 会话 + 输入 + 转写）
   ↓ 登出 / 票据失效
清票据 + 清 store + 卸载工作台树 → 回到登录页
```

### 3.2 三条实现约束

1. **走宿主同源路由，不要在浏览器直连 `services/*`**：避免 CORS，且服务地址与密钥留在宿主侧（浏览器 bundle 是公开产物，任何密钥打进 bundle 等于公开）。
2. **票据放 httpOnly Cookie，不要放 localStorage**：前端读不到才不会被 XSS 直接窃取；前端只需知道"是否已登录"与过期时间。
3. **宿主侧凭证来源用配置或 `ctx.credentials`**，不要硬编码；`services/authority` 的地址应可配置，便于本地/测试/生产切换。

### 3.3 安全边界（必读，别误解）

**浏览器侧的登录门只是 UX 门，不是安全边界。** 依据：

- `dsh web` 的 `/api` 只做 host/origin 的统一信任检查，**没有用户级鉴权**；任何能访问该端口的人都能直接 `POST /api/<namespace>/<method>` 驱动 agent，与前端渲染了什么无关。
- 会话数据面（连接、会话控制器、视图激活）在客户端启动后即已建立，**登录门只能不渲染，不能阻止数据流动**。

真正的强制点只有三处，按优先级：

| 方案 | 做法 | 强度 |
|---|---|---|
| 只绑回环 | 默认 `127.0.0.1`；不要用 `--trusted-host` 暴露到局域网 | 强（前提是不对外暴露端口） |
| 反向代理鉴权 | 在 DSH webserver 之前放一层带认证的代理（Nginx/Caddy/网关） | 强（推荐用于多人/远端） |
| 宿主侧校验 | 自定义路由与 Remote 方法自己校验票据；DSH 只提供载体 | 中（工作量在宿主） |

**结论**：登录页要做，但不要把它当成"保护 agent"的手段；对外的部署必须配 ①②。

### 3.4 路由与错误约定（建议）

- 路径前缀取 `/qs-auth/*`，与 DSH 的 `/api`、`/plugins` 不冲突（webserver 支持 exact 与 prefix 两类路由）。
- 未认证统一返回 401 + 结构化错误体；前端 auth store 收到 401 即复位并渲染登录页。
- 登出同时清宿主票据与前端 store；不要让"半登出"状态存在（例如票据已清但工作台树仍在）。

## 四、本阶段完成定义（DoD）

- [ ] 未登录访问 → 只有登录页，无任何工作台/会话内容泄漏到画面
- [ ] 登录成功 → 自动进入工作台主页（无需手动刷新）
- [ ] 发一条消息 → 助手流式输出出现在自建转写中
- [ ] 触发一次需审批的工具 → 自建审批卡出现 → 放行后工具继续
- [ ] 触发一次 `ask_user_question` → 自建提问表单出现 → 回答后 agent 继续
- [ ] 取消在跑的一轮 → 状态正确复位
- [ ] 登出 → 回到登录页且状态干净；重新登录 → 工作台正常恢复
- [ ] 全程看不到任何官方 UI 元素（sidebar / 设置 / 会话 / 品牌）

## 五、明确先不做（本阶段之外）

- 多会话并排布局（官方会话座位按"当前会话"解析，未验证，风险高）
- 主题/皮肤系统（先用官方 `--dsw-*` 令牌）
- 附件、`@` 引用、富文本输入（先把 send / cancel / queue 做扎实）
- 设置页、作业/调度/目标面板、第三方接口面板（见 [第三优先](03-第三优先-工作台差异化.md)）
- 为每个工具单独写专属视图（先用通用工具卡覆盖 90% 场景）
- **停用任何官方行**（遮蔽已足够；停用会因声明链断裂导致启动失败，见 [遮蔽对照表](04-遮蔽对照表.md)）
