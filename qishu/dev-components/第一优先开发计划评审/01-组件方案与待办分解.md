## 组件 1 · 登录页（静态）

**原型对照**：`app.js:98-101` `renderLogin()` —— 左故事栏（品牌 + eyebrow + h1「一个人，一句话。/看见全域，掌控全局。」+ 说明 + `factory.svg` + `story-footer`），右表单栏（`login-top` 帮助入口、`form-kicker`、h2「欢迎回到奇术」、用户名/密码字段、密码可见切换、自动登录 + 忘记密码、主按钮「登 录」、`#login-error` 错误区、演示账号提示、`login-bottom` 安全说明）。

**实现位置**：`src/client/login/`（`LoginPage.tsx`、`auth-store.ts`、`auth-gateway.ts`、`login.module.css`）。

**接口**：本阶段**无后端接口**。`AuthGateway` 仅作内部接缝（`signIn(credentials)` → 本地模拟校验 + 600ms 延时）。**不承诺**未来认证接口"零改动"：宿主侧接入（`/qs-auth/*`）会同时改动 gateway 实现与错误映射，届时按 [05](05-接口核对表.md) 补条目。

**槽与座位**：由外壳在 root occupant 内分支渲染；未登录**不挂载** session / session-maybe 子树（避免提前建立会话订阅）。

**状态与交互**：`idle | submitting | error`；字段校验（空值/长度）；密码可见切换（`aria-pressed`）；Enter 提交；提交中禁用 + loading 文案；错误 `role="alert"`；**不保存密码**（仅可选"自动登录"标记与用户名）。

**测试点**：store 状态迁移与"记住我"分支；存储不可用降级；三态渲染；密码切换；≤700px 分支。

**待办**

- [ ] `auth-store.ts`（登录态/用户名/记住我/登出；**不含密码**）+ 单测（含存储不可用）
- [ ] `LoginPage.tsx` 两栏 + 表单 + 错误区 + 演示账号块
- [ ] `login.module.css`（含 ≤1150/≤960/≤700 断点）
- [ ] 品牌组件与 `factory.svg` 按 [02](02-样式还原对照.md) 第五节三档策略接入
- [ ] 组件测试：三态 + 键盘提交 + 密码切换
- [ ] 登出路径：清 store → 回登录页 → 卸载工作台树

**验收**：与 `preview/login-desktop.png` / `login-mobile.png` 对照一致；未登录访问只看到登录页；登录后进入工作台且无需刷新；登出后状态干净。

## 组件 2 · 外壳骨架 + session 座位

**原型对照**：`app.js:115` `renderApp()` —— `header.topbar`（品牌 + 分隔线 + 平台标签 + 左栏开关；右侧状态 + 切换工作台 + 右栏开关）、`body-layout`（移动遮罩 + 侧栏 + 中区 + 右栏）；另见 `app.js:102-103`（侧栏）、`:108`（中区）、`:114`（右栏）。

**实现位置**：`src/client/shell/`（`AppShell.tsx`、`TopBar.tsx`、`SideNav.tsx`、`Stage.tsx`、`RightPanel.tsx`、`FrameOverlay.tsx`、`layout-store.ts`、`RootErrorBoundary.tsx`）。

**槽与座位（v3：以 [06](06-槽位与状态设计.md) 第二节为唯一依据）**

v2 曾把 `qs.stage.body` 同时交给 shell 与 composer、把 `qs.stage.transcript` 同时交给 transcript/approval/questions——**这在框架里不可能并列渲染**（同优先级抛错、不同优先级只渲染优胜者，[05](05-接口核对表.md) F6）。v3 槽树要点：

| 槽 | kind / scope | 贡献者 | 说明 |
|---|---|---|---|
| `root` | single / root | qs-shell（**负** priority） | 遮蔽官方 `AppFrame` |
| `qs.gate` | single / root | qs-login | 未登录时的登录视图（**新增**） |
| `qs.stage.body` | single / session-maybe | **仅 qs-shell** | 欢迎区 + 骨架 |
| `qs.stage.transcript` | single / session | **仅 qs-transcript** | 转写行 |
| `qs.composer` | single / session-maybe | **仅 qs-composer** | 输入区 |
| `qs.stage.interaction` | **chain** / session | qs-approval(1)、qs-questions(2) | **卡片位**：由 qs-transcript 声明并渲染（行列表末尾），位置同原型 |
| `qs.chrome` / `qs.nav` / `qs.stage` / `qs.inspector` / `qs.status` / `qs.overlay` | single|list / root | shell（qs-sessions 贡献 `qs.nav`；`qs.status` 为 list） | 见 06 |

**登录通路（解决"拆包后没有通路"）**：`qs-login` 用 `ctx.reflect.provide('qsAuth', auth)` 提供服务、用 `ctx.slots.provideRoot({ hooks: { auth } })` 暴露订阅；`qs-shell` 用 `useAuth` 决定首屏分支，用户区登出按钮经注册 `inject` 面调用 `signOut()`；**qs-login 缺失时 shell 视为已登录直通**（缺插件不得白屏）。细则见 [06](06-槽位与状态设计.md) 第三节。

**依据**：官方 `main.conversation` 自身即 `session-maybe`（`ui-conversation/src/client/apply.ts:415`），严格 session 槽在无绑定时抛错（`ui-renderer/src/client/scoped-slots.tsx:738-740`）。细则与状态所有权见 [06](06-槽位与状态设计.md)。

**开发者界面切换**：qs-shell 提供 defaultUi 与 showOfficialUiEntry，默认奇术且隐藏入口；显式开启后可双向切换，控制器和官方返回入口独立于奇术 root。启动、生命周期与停用排查规则统一见 [10](10-界面切换与回退配置.md)。

**状态与交互**：布局 store（`@deepseek-ai/dsh-client-store`）持有 `leftOpen/rightOpen/activeRightTab/compact/mode`，初始值来自视口（>700 左开、>960 右开）；折叠过渡 .2s；隐藏面板 `inert`；**根错误边界**：捕获渲染异常 → 渲染自建故障页（不把界面交给官方）。

**测试点**：store 断点策略与持久化；`inert`/`aria-expanded`；槽声明参数断言（含 `session-maybe` 与严格 `session` 各一处）；错误边界渲染故障页。

**待办**

## 组件 4 · 输入与发送（composer）

**原型对照**：`app.js:105` `composer()` —— 附件区、`textarea#prompt`、底部工具条（上传 / 分隔线 / 模型选择 / 深度思考 chip / 语音 / 发送或停止）+ 3 个建议 chips。

**实现位置**：`src/client/composer/`（`Composer.tsx`、`SuggestionRow.tsx`、`use-composer.ts`）。

**接口（v2 关键修订，逐条见 [05](05-接口核对表.md)）**

| 能力 | 接口 | 作用域 | 说明 |
|---|---|---|---|
| 草稿 | `inputActions.setDraft(text)` | 座位提供 | 也可 `pruneAttachments` |
| 提交（发送/排队） | `inputActions.submit()` | 座位提供 | 运行中提交的落点由提交策略决定（**排队语义需 M1 实测确认**，见下） |
| 停止 | **`ISession.cancel()`** | 会话对象 | `InputActions` **没有**停止；语义＝结束当前轮，**待发队列按 FIFO 继续** |
| 队列逐行操作 | `ISession.updateQueue(itemId, action)` | 会话对象 | 编辑/移除/引导按行进行；引导进入当前轮，不改变待发排序；失效时保留任务 |
| 整队引导 | ❌ 不可用 | — | `steerQueue()` 属 `ComposerKeyboard`，注释明确不跨插件边界 |
| 输入机自身状态 | `InputState`（经 `useInput`） | 座位提供 | 草稿 / 阶段 / claim / 队列；用于禁用与提示 |
| **外部阻塞原因**（v4 修正） | `ctx.conversation.blocks.storeFor(sessionId)`（`ComposerBlocks` 挂在 **`ctx.conversation`** 上） | 插件级服务（`inject: ['conversation']`） | 模型不可用等外部阻塞；只读 `useInput` **会漏掉**这类状态 |
| 模型 | 只读显示 | — | 切换留到设置/模型选择（第三优先） |

**状态与交互**：草稿保留；Enter 发送（Shift+Enter 换行）；IME 组合期不提交；运行中保留排队发送按钮，另设停止按钮；空输入禁用发送；建议 chip 填草稿；附件仅占位；发送/取消失败时**保留输入**并提示（见 [07](07-异常与恢复矩阵.md)）。

**提交冻结与交接**：捕获点击时文本与本地 opId，创建和交接期间只读。`draft` 清空且 `phase` 回稳仅说明官方输入机已乐观接管，不能证明远端成功。交接后允许新输入，失败恢复归官方输入机；自建层禁止回填旧 submittedText 覆盖新输入。详见 [06](06-槽位与状态设计.md) 第四节。pending 存在时禁用发送。

**M1 待实测项**：本地交接与延迟/乱序失败、新草稿保护、create/open 后 binding 就绪、chain owner props 与 fallbackOnly。逐条失败重试必须有公开、稳定的提交标识，否则仅做会话错误提示。

**测试点**：IME 守卫；Enter/Shift+Enter；空输入禁用；建议填入；生成时保留排队发送按钮，另设停止按钮；失败保留草稿；`cancel()` 文案与队列语义。

- [ ] `SuggestionRow.tsx` + 组件测试

## 组件 5 · 助手流式输出（最小转写）

**原型对照**：`app.js:107` `messages()` —— 用户气泡（右侧）+ 附件说明；助手 `article.message.assistant`（`ai-heading` 品牌 + 模型 + 状态；`ai-content` 段落 + 可选 `result-card`；`message-actions` 复制/重试/赞同）；`pending` 三点 + 文案。

**实现位置**：`src/client/transcript/`（`Transcript.tsx`、`UserMessage.tsx`、`AssistantMessage.tsx`、`PendingIndicator.tsx`、`ResultCardPlaceholder.tsx`、`adapter.ts`）。

**接口（v2 关键修订）**

- 快照形状：`ChatSnapshot = { order: readonly string[]; nodes: ChatNodeStore; locations; navigation; timeline; legacy }`（`ui-chat/src/client/contract/snapshot.ts:92-99`）。
- **正确迭代（v3 修正）**：按 `order` 取 key → 每个行组件用**自己绑定的 keyed hook** 订阅自身。注意 **`useChatNode` 不是框架自动提供的座席**：官方是在自己的注册里通过 `children.inject.keyedHooks` 提供的（`ui-chat/src/client/apply.ts:105,116-119`：`chatNode: key => chat.getSnapshot().nodes.source(key)`）。`qs-transcript` 必须照此自建（见 [06](06-槽位与状态设计.md) 第五节）。**禁止**在每个流式增量上重转全量历史，也**禁止**在业务组件里手工 `subscribe`。
- **真实节点 kind**（`ChatNodeKind` 由 `ChatNodeDataMap` 声明合并而来）：实测至少包含 `assistant-step`（`conversation-nodes/assistant.ts:294`）、`user`、`steering`、`context`（`chat-snapshot-builder.ts:737-739`），以及 tool / compaction / command / fallback / turn-process / turn-error / turn-tail / turn-max-tokens / request-prompt / retry 等模块 kind。v1 写的 `assistant`/`message` 是 Definition 名，**不是**节点判别式。
- **`legacy` 投影不得作为渲染主路径**（它是兼容层，`contract/snapshot.ts:82-89`）。
- 流式：`AssistantChatData.status: 'running' | 'settled' | 'interrupted'` + `blocks`（文本/推理块）。

**状态与交互**：按 kind 分派（本阶段至少 `assistant-step`/`user`/`steering` + 通用 `fallback`）；生成中 pending 三点；自动滚动（用户上滚不抢夺）；消息动作按"官方是否提供对应动作"核对后决定显示（复制优先，重试/赞同无对应则隐藏并记入 [08](08-视觉差异清单与新增交互稿.md)）；长文本与代码块可读性策略（Markdown 子集 + 链接处理 + **禁止 innerHTML**）在 M1 定稿并写入 [08](08-视觉差异清单与新增交互稿.md)。

**测试点**：kind 分派与未知兜底；`order`+keyed reader 渲染（不重转全量）；流式追加与历史回放一致；自动滚动策略；pending 显隐；动作可用性降级。

- [ ] `UserMessage.tsx` / `AssistantMessage.tsx` / `PendingIndicator.tsx` / `ResultCardPlaceholder.tsx` + 组件测试

## 组件 6 · 审批呈现与回答（阻塞项）

**原型对照（v3 更新）**：`interactions.js` 的 `approval` 与 `fallback`（详情不可用）场景，验收基准 `interaction-approval-{1440,390}-{light,dark}.png` —— 原型已由需求方提供，**进入 1:1 还原范围**（见 [08](08-视觉差异清单与新增交互稿.md)）。

**实现位置**：`packages/qs/qs-approval/src/client/approval/`（`ApprovalCard.tsx`、`use-pending-approval.ts`、`approval-detail.ts`）。

**槽与座位（v4 定案）**：卡片挂在 **`qs.stage.interaction`（chain，session）**，宿主是 **qs-transcript**（在其行列表末尾 `renderSlotChain('qs.stage.interaction', {}, { fallback: null })`）——**与原型一致**：卡片位于消息流末尾（原型 `messages()` 内 `${interactionView()}`），composer 仍在下方但**禁用**。`select` 命中当前会话的 pending 时渲染本卡；全部为 null 时渲染 `null`。pending 从 root 的 `useSessionPendingInteraction` 读取（`ui-session/src/client/index.ts:507-512`）。**chain 条目崩溃不退位**（`abdicate: spec.kind !== 'chain'`）⇒ 卡片必须自带错误提示 + 重试（[07](07-异常与恢复矩阵.md) T1b）。

**接口（v2 修订）**

- 数据：`useSessionPendingInteraction` → `kind === 'approval'` → `PendingApproval { key, toolName, callId?, reason?, result }`；动作 `answer('allowed-once' | 'rejected')`、`delegate()`、`abort(reason)`。
- **详情**：官方详情来自 `conversation.approval.detail` 子槽，而该槽由 ui-approval 自己声明（`ui-approval/src/client/index.ts:86-88`）——我们不是它的父，**无法渲染**。故：按 `callId` 从会话数据自解析调用（命令/参数/目标），解析不到时给**安全文本兜底**（只显示工具名与原因）。

**生命周期（v2 修订，见 [07](07-异常与恢复矩阵.md)）**

| 事件 | 正确行为 |
|---|---|
| 切换会话 / 组件卸载 | **不得** abort 或 answer；请求由官方域注册持有，切回后从快照重建视图 |
| HMR 重载 | 同上；视图重建，不重复答复 |
| 请求被 Host 撤销 | `result` reject / `signal` abort → 卡片消失，不显示为"用户拒绝" |
| 会话真正结束 | 由官方生命周期处理，我方只停止渲染 |
| 快速重复点击 | 提交后立即禁用（参照官方 `answered` 状态机） |

**键隔离**：视图状态按 `sessionId + pending.key` 隔离，避免跨会话复用错误状态。

- [ ] `approval-detail.ts`（callId → 详情，含兜底）+ 单测

## 组件 7 · 用户提问呈现与回答（阻塞项）

**原型对照（v3 更新）**：`interactions.js` 的 `questions` / `free` / `plan` / `approve-only` 四个场景，验收基准 `interaction-questions|plan-{1440,390}-{light,dark}.png` —— 原型已由需求方提供，**进入 1:1 还原范围**。

**实现位置**：`packages/qs/qs-questions/src/client/questions/`（`QuestionForm.tsx`、`PlanReviewCard.tsx`、`use-pending-question.ts`）。

**槽与座位（v4 定案）**：与审批共用 **`qs.stage.interaction`（chain，session）**，priority 排在审批之后（`qs-approval` = 1、`qs-questions` = 2），由 `select` 按当前会话 pending 的类型命中；宿主同为 qs-transcript。pending 从 **root 的 `useSessionPendingInteraction`** 读取。表单草稿按 `sessionId + pending.key` 归 `qs-questions` 所有（HMR 后丢失，见 [06](06-槽位与状态设计.md) 第七节）。**崩溃不退位** ⇒ 卡片自带错误提示 + 重试。**无退出的提问流程**：第一优先只提供"作答并提交"，不做跳过/取消——若需要，属产品决策，不得由实现自行发明（记入 [04](04-需求追踪表.md)）。

**接口（v2 补齐）**

- 数据：`useSessionPendingInteraction` → `kind === 'question' | 'plan-review'` → `PendingQuestion.answer(answer)`。
- 答案协议（`interaction/user-questions/src/types.ts:51-64`）：`{ answers: [{ id, selected: string[], custom?: string }] }`，**`custom` 与 `selected` 在多选下可并存**。
- 问题项：`id / question / detail? / header? / options? / multiSelect? / intent?`；**支持多问题批次**（一个请求包含多题）。
- **plan-review 判定**（`ui-user-questions/src/client/contract/slots.ts:77-96`）：单问题、带 `detail`、非多选、选项 ≤2、`approve` 标签由 `intent.approve` **按名字**匹配；**`decline` 可缺失**（只有批准选项时合法）——不得按位置或固定文案推断。

**状态与交互**：单选 / 多选 / 自由填写（有选项时提供 Other 输入）/ 多选 + 自由文本；多问题按顺序渲染并整体提交；提交中禁用；提交失败可重试；请求撤销时卡片消失。

**测试点**：三形态 + Other + 多问题批次；plan-review 仅批准分支；答案结构（标签原样回传、`custom` 正确挂载）；撤销处理。
