## 七、M1 仍需运行验证的清单（阻塞项）

> 原 1–3 条已升级为上方事实（F1–F3），以下沿用原编号以便追溯。

1. ~~运行中提交的落点~~ → **已升级为上方 F1**（`submit()` 固定 `'queue'`）。
2. ~~无会话时是否自动建会话~~ → **已升级为上方 F2**（无会话时 `inputActions` 为 `undefined`，流程见 [06](06-槽位与状态设计.md) 第四节）。
3. ~~cancel 的返回与队列行为~~ → **已升级为上方 F3**（结束当前轮、保留队列）。
4. `binding(id).session` 在 `session-maybe` 子树内是否可直接取得（还是必须经 hook）。
5. `useSessionPendingInteraction` 在多会话下的切换表现（A 的 pending 是否在切回后仍可取）。
6. 连接状态取值集合与手动 `reconnect()` 的可达性（从第三方插件调用）。
7. **单选 + 自由文本**：原型按"清空选中项、`custom` 携带文本"处理（`selected: []`），需实测宿主是否接受空 `selected`；若必须至少一项，则改为把"其他"标签也放进 `selected`。
8. **多问题批次是否要求全部作答**：原型按必答处理并聚焦首个未答项；需与官方 `QuestionComposer` 的实际行为比对后再定。
9. **审批详情派生**：由 `callId` 关联到工具调用后，能稳定得到哪些字段（命令 / 参数 / 目标 / 影响）；其余一律走兜底文案（原型已给兜底样式）。
10. **`PendingApproval.delegate()` 的产品语义**：我们不做该按钮，需确认"不答复即不 delegation"、且域注册在请求结束时才移除。
11. **数据源可达性三连**：`ctx.conversation.blocks.storeFor(sessionId)` 从第三方插件调用是否可用；工作区归档集合在客户端经哪个字段读取（`ctx.workspaces` 面）；`ChatNodeStore.source(key)` / `processSource(key)` 的键来源与生命周期。
12. **`qs.stage.interaction`（chain，session）的接管行为**：`select` 命中时卡片位置是否与原型一致；宿主 qs-transcript 的 `renderSlotChain(..., { sessionId, pendingInteraction }, { fallback: null })` 是否有副作用；chain 条目抛错后的错误面与"请求仍 pending"能否恢复（见 [07](07-异常与恢复矩阵.md) T1b）。
13. **本地交接与延迟失败验证（[06](06-槽位与状态设计.md) 第四节 ②）**：验证 draft 清空与 phase 回稳仅表示本地交接；验证延迟失败不覆盖新草稿、乱序失败、切会话归属；核实是否存在稳定的公开逐条失败读面，无则不提供自建逐条重试。
14. **`opId` 的本地编排边界**：确认 `submit()` 不接受参数、官方无远端幂等；重试语义按"未创建成功 vs 已创建后"两条路径实测（尤其重复点击与快速重试）。
