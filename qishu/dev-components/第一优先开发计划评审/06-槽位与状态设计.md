# 槽位与状态设计（第一优先，v3：组合接线修订）

> **v3 修订动机**：v2 把多个包安排进同一个 `single` 槽，这在框架里不可能同时渲染；同时登录拆包后缺少跨包数据通路、无会话发送没有确定流程、pending 挂载点放错作用域。本文件重画槽树并给出完整通路。
> 上级：[评审总纲](00-评审总纲.md)　接口：[05](05-接口核对表.md)　异常：[07](07-异常与恢复矩阵.md)　组件：[01](01-组件方案与待办分解.md)

## 一、single 槽的硬事实（v2 错误的根源）

| 行为 | 结果 | 依据 |
|---|---|---|
| 同优先级重复注册 | **直接抛错** | `ui-slots/src/index.ts:839-841` |
| 不同优先级注册 | 共存但**只渲染优胜者**（最低者），不是并列 | `ui-slots/src/index.ts:834` + 排序规则 |

⇒ **需要多个包同时出现的位置，一律不能用 `single`**：用 `list`（并列条目）、`keyed`（按 key 分派）或 `chain`（按 `select` 选举接管）。官方正是这样做的：`conversation.composer` 是 **chain**，审批用 `select` 接管输入区（`ui-conversation/src/client/apply.ts:248`；`ui-approval/src/client/index.ts:80-89`）。

## 二、槽树 v3（每个 entry 的贡献者 / 子槽 / props / inject）

注册总入口：`qs-shell` 一次性 `ctx.slots.register({ name:'root', priority:<负>, children:{…} }, AppShell)`。

| 槽 | kind | scope | 声明者 | 贡献者 | 说明 |
|---|---|---|---|---|---|
| `root` | single | root | qs-shell | qs-shell 渲染 | 负优先级遮蔽官方 `AppFrame` |
| `qs.gate` | single | root | qs-shell | **qs-login** | **新增**：登录视图挂载点（未登录时渲染） |
| `qs.chrome` | single | root | qs-shell | qs-shell | 顶栏（品牌 / 折叠开关 / 状态入口） |
| `qs.nav` | single | root | qs-shell | **qs-sessions** | 左导航：会话列表容器 |
| `qs.stage` | single | root | qs-shell | qs-shell | 主区外框 |
| `qs.stage.body` | single | **session-maybe** | qs-shell | **qs-shell** | 欢迎区 + 骨架（**不再由 composer 共同贡献**） |
| `qs.stage.transcript` | single | **session** | qs-shell | **仅 qs-transcript** | 转写行；审批/提问**不放这里** |
| `qs.composer` | single | **session-maybe** | qs-shell | **qs-composer** | 输入区（无会话时也渲染，但 `inputActions` 为 `undefined`） |
| `qs.stage.interaction` | **chain** | **session** | **qs-transcript**（作为 `qs.stage.transcript` 的**子槽**声明并渲染） | **qs-approval**（priority 1）、**qs-questions**（priority 2） | **卡片位＝原型位置**：转写流末尾（原型 `messages()` 内 `${interactionView()}`，紧跟消息列表、在 pending 三点之前）。`select` 命中当前会话的 pending 时渲染该卡；全部返回 `null` 时宿主渲染 `null` |
| `qs.inspector` | single | root | qs-shell | qs-shell | 右栏（骨架 + 空态） |
| `qs.status` | list | root | qs-shell | qs-shell、qs-sessions | 底部状态条（连接态 / 同步态） |
| `qs.overlay` | list | root | qs-shell | qs-shell | toast / dialog 宿主（portal 目标） |

**声明权规则（v4 澄清，消除"shell 声明全部 vs 子槽自建"的冲突）**

- `qs-shell` 声明**顶层** `qs.*` 槽（上表除 `qs.stage.interaction` 外全部）。
- **每个 entry 可以声明并渲染自己的子槽**——官方同款：`ui-conversation` 的 `main.conversation` entry 自己声明并 `renderSlotChain('conversation.composer', …)`（`skeleton/ConversationRoot.tsx:356`）。
- 因此 `qs.stage.transcript.row`（keyed）与 `qs.stage.interaction`（chain）**由 qs-transcript 声明**，它同时是这两个槽的渲染宿主。两者不矛盾：前者说的是顶层归属，后者说的是"谁拥有并渲染这个位置"。

**entry 契约要点**（实现时逐条对照）：

- `qs.stage.interaction`（chain/session）的宿主是 **qs-transcript**：**宿主先取当前 pending，再把选择器需要的字段显式传入** —— `renderSlotChain('qs.stage.interaction', { sessionId, pendingInteraction }, { fallback: null })`。官方同款：`ConversationRoot.tsx:356-360` 传的是 `{ sessionId, session, pendingInteraction }`。**选择器只拿到宿主传入的 owner props，框架不会自动补字段**（这是 v4 示意的错误，会导致卡片永不出现）；两个贡献者各自声明 `select`，命中时返回非空（`ChainSelect` 语义：按 priority 升序，第一个非 null 者当选）。
- **composer 不参与接管**：pending 存在时，`qs-composer` 读 root 的 `useSessionPendingInteraction`（按当前 sessionId）→ 禁用发送并保留草稿；用户仍点发送时给提示（原型同款："请先完成对话中的确认，再发送新任务"）。
- `qs.stage.transcript` 的 entry 在 `inject` 面暴露 **keyedHooks**（第五节给出精确数据链）。
- 所有贡献者都用 `ctx.slots.inject(key, () => ctx.slots.register(...))`——声明撤销时贡献自动清理，重新声明后重新安装（框架已验证行为）。

## 三、登录：跨包数据通路（解决"拆包后没有通路"）

`qs-login` 拥有登录视图与登录态；`qs-shell` 决定首屏分支。两者**不能互相 import 运行值**，因此走服务 + root hook：

```
qs-login                                 qs-shell
  ├─ 拥有 auth store（登录态/用户名/记住我）        │
  ├─ ctx.reflect.provide('qsAuth', auth)  ────────→ 可选读取：ctx.get('qsAuth')（登出按钮调用；**不写进 inject**）
  └─ ctx.slots.provideRoot({ hooks:{ auth } }) ───→ 组件内 useAuth(selector) 决定首屏分支
       └─ 视图贡献到 qs.gate ─────────────────────→ 未登录时渲染 qs.gate
```

| 事项 | 结论 |
|---|---|
| 服务名与面 | `qsAuth`（`ctx.reflect.provide`，先例 `ui-layout/src/client/index.ts:147`）；观察面必须是 **`{ getSnapshot(): AuthSnapshot; subscribe(listener): () => void }`**（框架要的是 HostObservable，**不是** `snapshot()`）；动作：`signIn(credentials)` / `signOut()` |
| 订阅方式 | `ctx.slots.provideRoot({ hooks: { auth } })`（先例 `ui-session/src/client/index.ts:507`、`ui-layout/src/client/index.ts:146`）；组件用 `useAuth(selector)`，**不手工订阅** |
| **依赖形态（v4 修正）** | shell **不**把 `qsAuth` 写进 `inject`（必需服务缺失会让 fiber 一直等待，永远走不到"直通"分支）。改为**可选读取**：`ctx.get('qsAuth')`（先例 `ui-conversation/src/client/apply.ts:120` 的 `ctx.get('conversation')`），或 `ctx.inject(['qsAuth'], …)` 在服务出现时装回调 |
| 首屏分支 | 未登录 → 渲染 `qs.gate`，不挂载 session 子树；已登录 → 渲染工作台树 |
| 登出回调 | shell 用户区按钮经注册 `inject` 面暴露 `signOut: () => ctx.get('qsAuth')?.signOut()`；调用后清本地登录态 → `useAuth` 变化 → 回到 `qs.gate` |
| **qs-login 缺失（v5 定案）** | **正常交付组合必须包含 `qs-login`**；缺失时 shell 渲染**明确的组件加载故障面**（"登录组件未加载" + 诊断信息），**不静默直通**。若确实需要无登录模式，用**显式配置**（如 `qsAuth` 的 `mode: 'open'`）表达，而不是"某个包没装"的隐式结果。任何模式都必须写明：**静态登录不是安全边界** |
| **M0/M1 依赖（v4 修正）** | `qs-login` **不是空骨架**：M0 起它就提供 `qsAuth`（静态 `getSnapshot() = { authenticated: true }`）与 `qs.gate` 占位；M2 才补登录页与真实分支。这样 shell 从 M0 起就有可用的 auth 提供者，与里程碑不冲突 |
| 不做的 | 不做权限模型；票据与宿主侧接入（`/qs-auth/*`）后置 |

## 四、无会话发送：确定性流程（解决"两种分支"悬案）

**已确认的源码事实**（无需实测）：

- 无当前会话时，session 贡献的 hooks/keyedHooks/props **全部为 `undefined`**（`ui-session/src/client/index.ts:428-439` 的 `materializeAbsent()`），其中包含 `inputActions`。
- `session-maybe` 只让**界面**存在，不会赋予可用的发送动作。
- 公开 `inputActions.submit()` 固定执行 `submit('queue')`（`ui-conversation/src/client/input/facade.ts:142`）——**运行中提交＝进入队列**，这条悬案关闭。

**流程（qs-composer 实现）**：

```
无会话时：草稿归属 qs-composer 的本地 compose store（session-maybe 作用域，按"未归属草稿"单例）
用户点发送 → **冻结本次提交**：capture `submittedText`（点击时文本）+ 本地 `opId`
             （`opId` **只由本地编排器持有**，不传给官方接口——`InputActions.submit()` 无参数，官方也没有远端幂等承诺）
             输入区进入 frozen（只读 + "正在发送…"）
  ├─ 若 inputActions 存在（已有会话）→ setDraft(submittedText) → submit()
  └─ 若 inputActions 为 undefined（无会话）：
       置 in-flight（`opId` 仅用于**本地**防重复点击与隔离异步回调）
       → sessions.create({ workspaceId?, cwd? }) → sessions.open(id)
       → 等 session-maybe 重新物化出真实 sessionId（binding 就绪）
       → setDraft(submittedText) → submit()
阶段与判据（三层各自可观察，**不依赖单一字段**）：
  ① 交接确认：`useInput().draft === submittedText`（setDraft 已生效）
  ② **本地交接判定，不是远端接收凭证**
       - `draft` 清空且 `phase` 回稳只说明官方输入机已乐观接管本次发送；可以清本地未归属草稿并解冻。
       - 仲裁后草稿仍保留时，显示“未发送，草稿已保留”；不得以 `promptError === null` 判成功。
       - 官方默认发送是 detached：phase 可在远端完成前回到 plain（`input/machine.ts:127-142`）。
  ③ **延迟失败与新输入**
       - 一旦交给官方输入机，会话草稿及失败恢复由官方输入机管理（`input/facade.ts:791`）。
       - 自建层不得在错误回调中 `setDraft(submittedText)`；用户可能已经输入 B，A 的失败不能覆盖 B。
       - `promptError` 仅显示会话错误，不能关联单次提交或证明远端接收；它也可能来自停止等操作。
       - 原型独立失败卡用于演示保留失败内容与新草稿；正式实现先在 M1 核实公开读面。无稳定提交标识时只做错误提示与官方草稿恢复，不伪造逐条远端重试入口。
  本地交接完成 → 清本地 compose store 与 frozen，后续状态归官方输入机。
  创建/open/交接前失败 → 仅在仍属于本地冻结操作时保留 submittedText，解冻；不得覆写其他会话草稿。
重试语义（分开定义，不要笼统写"同一 opId 不重复 create"）：
  - **尚未创建成功**的重试：不得复用上一次的 create 结果（没有），重新走 create → open（同一 `opId` 只防重复点击）
  - **已创建会话后**的重试：复用已有 `sessionId`，只重做 setDraft → submit()，**不得再次 create**
取消语义：
  - **提交前**取消（尚未调用 `submit()`）：丢弃本地编排、清 frozen，安全
  - **已调用 `submit()` 后**：不存在"取消发送"——只能 `ISession.cancel()`（结束当前轮）或 `updateQueue(itemId, …)`（移除已入队项）；二者都不等于撤回已投递内容
```

**竞争与失败**：

| 情况 | 处理 |
|---|---|
| 创建期间用户**想继续编辑** | 输入区在 frozen（"正在发送…"）期间**只读**——从根上排除"点击后新输入被一起发出"；用户可等待，或点"取消本次发送" |
| 用户点"取消本次发送" | **区分阶段**：提交前取消＝丢弃本地编排、解冻（安全）；已 `submit()` 后**没有"取消发送"**，只能 `cancel()`（结束当前轮）或 `updateQueue(itemId, …)`（移除排队项），并如实告知用户"已投递，只能停止或撤回排队" |
| 创建期间切换会话 / 登出 | 按捕获的 `sessionId` 比对，丢弃 in-flight 的 UI 写入；不清空用户草稿（见第八节） |
| 创建前失败 | 无新会话；回填 `submittedText`；解冻；提示可重试；未创建成功时允许重新 create |
| 创建后工作区挂接失败 | **会话已创建**（错误带 `sessionId`，客户端已按未分组发布，见 [07](07-异常与恢复矩阵.md) 第 6b 条）；**不重复 create**；提示"已创建，未归入工作区"，可手动打开 |
| open 失败 | 会话在列表中；提示手动打开；草稿回填 |
| submit 阶段未接收 / 远端失败 | 交接前保留本地草稿；交接后由官方输入机恢复，禁止无条件回填；错误不清除新输入。已创建则复用 sessionId，不重复 create |

## 五、转写：自建 keyed hook 注入路径（解决"useChatNode 不会自动出现"）

**事实（v4 修正：两段机制不能混）**：官方把"行订阅"和"子槽公共 hook"分成两件事——

| 机制 | 位置 | 提供什么 |
|---|---|---|
| **entry 的 `inject` 面** | `ui-chat/src/client/apply.ts:109,116-119`（注册 `conversation.view` 这个 entry 时返回） | `keyedHooks: { chatNode: key => …, chatNodeProcess: key => … }` → 框架绑成行组件的 `useChatNode(key)` / `useChatNodeProcess(key)` |
| **子槽的 `inject` face** | `ui-chat/src/client/contract/slots.ts:76` 的 `CHAT_NODE_INJECT` | `hooks: { turnData }`（即 `useTurnData`），**与 keyedHooks 无关** |

**精确数据链（qs-transcript 照此实现）**：

```
ctx.sessions.binding(sessionId)                       // SessionBinding（插件侧，apply 作用域）
  → ctx.uiConversation.binding(binding).target('chat') // 官方装配面：chat target source
  → source.getSnapshot().nodes.source(key)             // 行数据源（processSource 同理）
  → 作为 entry 注册的 inject 面返回 { keyedHooks: { node, process } }
  → 框架把 keyedHooks 绑定成行组件的 useNode(key) / useProcess(key)
  → 行组件只读 node.data，不手工 subscribe
```

官方原始写法就在 `apply.ts:58-70`（`chatSource(binding)` 用 `WeakMap<SessionBinding, source>` 缓存）+ `:116-119`（keyedHooks）；`qs-transcript` 复制这个**形状**，不复制代码。类型仍只用 `import type`（`ChatNode` / `ChatNodeKind` / `ChatSnapshot`）。子槽 `qs.stage.transcript.row`（keyed）可另设自己的 `inject` face（例如未来需要 `turnData` 时），与上面的 entry keyedHooks 互不替代。

## 六、pending 请求：root 提供，不依赖严格 session 座位（v2 修正）

`useSessionPendingInteraction` 来自 **`provideRoot`**（`ui-session/src/client/index.ts:507-512`：`hooks: { sessions, sessionPendingInteraction }`），因此：

- **root 作用域即可读取**；关键是按当前 `sessionId` 从 Map 取值（`ReadonlyMap<SessionId, SessionPendingInteraction>`）。
- 审批/提问的卡片位是 **`qs.stage.interaction`（chain，session，宿主 qs-transcript）**，**不是** `qs.stage.transcript`（single，只有一个贡献者）——两者都不需要严格 session 座位。

| 事件 | 视图 | 请求 | 动作 |
|---|---|---|---|
| 挂载（有 pending） | 卡片出现在**消息流末尾**（composer 保留但禁用） | 存活 | 从快照重建，键＝`sessionId + pending.key` |
| 切换会话（卸载） | 消失 | **继续存活** | **不得** abort/answer；切回重建 |
| HMR 重载（**qs-approval/qs-questions 自身**） | 重建 | 取决于请求持有者 | 见下方 HMR 承诺边界 |
| 用户答复 | 禁用→消失 | settle | `answer(...)`；失败恢复可点并提示 |
| Host 撤销 / signal abort | 消失 | 结束 | 只停止渲染；**不显示为"用户拒绝"** |
| 快速重复点击 | — | — | 提交即禁用 |
| **卡片自身渲染抛错** | **chain 不退位**：`abdicate: spec.kind !== 'chain'`（`scoped-slots.tsx:750-756`）⇒ 该位置显示框架错误面，**不会自动换下一个候选** | 错误面 | 请求**仍 pending** | 卡片必须组件内自带错误提示 + 重试（对应原型 `system-fault` 的"重试渲染"）；**不得**依赖"换候选" |

**HMR 承诺边界（修正 v2 的过宽表述）**：pending 请求由**官方域注册**持有（`ui-approval` / `ui-user-questions`）。因此：
- 只有**我们自己的视图插件**热更新时，请求仍存活，重建后可继续作答；
- 若**请求持有者（官方包）**被热更新或卸载，请求按其自身生命周期处理，我们**不承诺**其存活。
- 我们自己的表单草稿（见第七节）在 HMR 后丢失，属已知代价。

## 七、状态所有权与持久化（v3 补充）

| 状态 | 归属（包） | 组件重挂 | 插件 HMR | 刷新 | 清理 |
|---|---|---|---|---|---|
| 登录态 / 用户名 / 记住我 | qs-login（**不含密码**） | 保持 | 从存储重读 | 保持（记住我） | 登出清空 |
| 布局（折叠/宽度/活动标签） | qs-shell | 保持 | 从存储重读 | 保持 | 回退时清 |
| 本地置顶 pin | qs-sessions | 保持 | 从存储重读 | 保持 | 归档时一并清理该会话的 pin |
| **未归属草稿（无会话）** | qs-composer（本地 compose store） | 保持 | 丢失（可接受） | 丢失 | 交接成功后清空 |
| 会话内草稿 / 附件 | 官方输入机（按会话） | 保持 | 官方域持有 | 依官方 | 切换会话各自独立 |

| 当前会话 | 官方 `sessions.list` | 保持 | 保持 | 保持 | — |
| 主题 | **主题选择来源**：第一阶段跟随官方 `ui-theme`（读 `ctx.theme`）；**颜色令牌来源**：qs-shell 自建 `--qs-*` | 保持 | 保持 | 保持 | — |
| 错误 / 失败态 | 各组件本地 | 丢失 | 丢失 | 丢失 | 随组件 |

> **主题来源必须分开说**：v2 的"自建 `--qs-*`"指的是**令牌**；明暗选择这一阶段跟随官方主题（自建切换入口属设置页，后置）。二者不矛盾。

## 八、跨会话异步归属规则（保留）

1. 每个异步调用发起时**捕获 `sessionId`**，写回前与当前会话比对；不一致则丢弃 UI 写入。
2. 禁止模块级可变单例保存会话相关状态；缓存用 `Map<SessionId, …>` 并显式清理。
3. 订阅按会话键隔离（官方做法：`WeakMap<SessionBinding, source>`，`ui-chat/src/client/apply.ts:58-70`）。
4. 错误提示归属发起会话，或全局 toast 带会话标识。
5. 滚动位置、自动滚动意图、输入焦点同样按会话隔离。

## 九、关于 `session-maybe` 的定位（软化 v2 的绝对表述）

- **硬约束只有一条**：严格 `session` 槽在无绑定时抛 `SlotAssemblyError`（`ui-renderer/src/client/scoped-slots.tsx:738-740`）。
- `session-maybe` 是让"无会话时仍要渲染"的位置继续存在的**一种**实现方式（官方 `main.conversation` 即如此，`ui-conversation/src/client/apply.ts:415`）；**在 root 作用域直接渲染无会话内容同样合法**。
- 本方案采用 `session-maybe` 的理由是"输入区要跟随会话绑定以便拿到 `inputActions`"，属设计选择，不是框架强制。

## 十、最小类型化接线（三段示意，非最终代码）

> 目的：把上面三条最容易写错的数据链压成可对照的形状。字段名以官方类型为准，落地时按 `import type` 取；此处仅为"谁提供、谁消费、形状如何"。

**① 登录状态（qs-login 提供 / qs-shell 消费）**

```ts
// 提供方（qs-login）——观察面必须是 HostObservable，不是 snapshot()
export interface AuthSnapshot { readonly authenticated: boolean; readonly user?: string }
const source = {
  getSnapshot: (): AuthSnapshot => state,
  subscribe: (listener: () => void): (() => void) => subscribe(listener),
}
ctx.reflect.provide('qsAuth', { ...source, signIn, signOut })
ctx.slots.provideRoot({ hooks: { auth: source } })     // root 作用域组件得到 useAuth(selector)

// 消费方（qs-shell）——不要把 qsAuth 写进 inject（否则常量 PENDING）
const signOut = (): void => { ctx.get('qsAuth')?.signOut() }   // 先例 ui-conversation/apply.ts:120
// 组件：const authed = useAuth(s => s.authenticated)  ← 来自 root 标准座席
```

```ts
        node: (key: string) => snapshot()?.nodes.source(key) ?? EMPTY_NODE_SOURCE,
        process: (key: string) => snapshot()?.nodes.processSource(key) ?? EMPTY_PROCESS_SOURCE,

  },
```

**③ chain 接管（宿主 qs-transcript / 贡献方 qs-approval・qs-questions）**

```ts
// 贡献方：select 命中当前会话的 pending 才返回非空
ctx.slots.inject('qs.stage.interaction', () => ctx.slots.register({
  name: 'qs.stage.interaction',
  priority: 1,                                    // 审批 1、提问 2（升序选举，第一个非 null 当选）
  select: ({ sessionId, pendingInteraction }) =>
    sessionId !== undefined && pendingInteraction?.kind === 'approval' ? pendingInteraction : null,
}, ApprovalCard))

// 消费方（组件内）：pending 来自 root 座席，按当前 sessionId 取
const pending = useSessionPendingInteraction(m => sessionId === undefined ? undefined : m.get(sessionId))
```

**边界提醒**：chain 条目崩溃**不退位**（`abdicate: spec.kind !== 'chain'`）⇒ `ApprovalCard` / `QuestionForm` 必须自带错误提示 + 重试；单/键/列表条目崩溃才退位。

## 十一、样式共享的边界（补充）

全局类名（`.qs-*`）只共享**外观**。以下行为**不能**靠类名复用，必须各自实现或经官方机制：
- 弹窗焦点约束与关闭后焦点恢复；
- 键盘交互（Tab 顺序、Esc 关闭、方向键）；
- 错误边界与空态文案；
- 表单校验与可访问名。

`qs-shell` 提供的是**令牌 + 类名 + overlay 宿主**；行为层每个包自己负责，交叉包行为只经槽或 cordis 服务。

## 十二、组合状态与操作规则

- 每次客户端新投递前检查连接、模型、pending 与会话加载状态，包括首次 create/open 完成后和手动继续暂停队列。阻塞时不消费本地待发项，恢复后可重试；这不要求断线时停止 Host 已接收的任务。
- 队列逐条“引导当前轮”使用 `updateQueue(itemId, {kind:'steer'})`；仅当前轮运行且任务仍待发时可用。当前轮已结束的竞争失败保留任务并提示，不能模拟为队列排序。
- 第一优先的归档入口只允许空闲、无待发任务且无 pending 的会话。确认时重新检查；不主动 cancel、不清队列、不代答。客户端检查不是 Host 原子锁；远端变化仍以真实快照为准。
- 转写按 sessionId 保存 scrollTop 与 followLatest；返回会话时按各自意图恢复。历史前插用可见消息锚点保持阅读位置；原型本地示例不能代替真实分页合并验收。

## 开发者界面切换的生命周期

界面切换控制器由 qs-shell 持有，独立于可释放的奇术 root 注册；官方返回入口通过经 M1 验证的官方公共扩展槽贡献，不属于 qs.* 子槽。各插件草稿与滚动 store 不随视图切换销毁；官方请求持有者保持加载，切换不 cancel、不 answer、不 signOut。配置关闭时不贡献入口且拒绝切换动作，刷新按启动默认界面初始化。完整行为见 [10](10-界面切换与回退配置.md)。
