# 第二优先：转写补齐——让 agent 的工作可读、可诊断

> **阶段目标**：从"能看见 agent 在动"升级到"能看清它在做什么、为什么慢、为什么失败"。本阶段结束后，长任务的绝大多数疑问都能在界面内回答，不必回去看终端日志。
>
> **前置条件**：[第一优先](01-第一优先-最小可用工作台.md) 全部完成（外壳、会话、输入、最简助手转写、审批与提问）。
>
> **相关文档**：[第三优先](03-第三优先-工作台差异化.md) · [遮蔽对照表](04-遮蔽对照表.md) · [第一优先开发计划评审](第一优先开发计划评审/00-评审总纲.md)
>
> 文档约定：本文件非 `README.md`、不带 `.i18n.yaml`，不在 DSH 双语语料库与 doc-sync 门禁范围内。

## 一、排序原则

按**信息密度**排，不按视觉复杂度排：先做"没有它就看不到主线"的行，再做"锦上添花"的行。

## 二、组件清单（按开发顺序）

| 顺序 | 组件（对应 chat 节点 kind） | 作用（为什么必须 / 不做会怎样） | 对应官方原组件 | 数据来源 | 验收标准 |
|---|---|---|---|---|---|
| **1** | **工具调用卡**（`tool`） | agent 的行为几乎全部经由工具（读写文件、执行命令、搜索、子代理）。不做它，转写几乎是空的——**信息密度最高的一行**；也是用户判断"它到底改了什么"的唯一依据 | `ui-tool`（各工具专属视图）、`ui-chat` 的 tool 定义与渲染 | `useChat` → tool 节点（先只读 `node.data`；工具专属视图是第二层） | 一次读写文件、一次执行命令都能正确显示调用参数与结果 |
| **2** | **轮次/步骤进度**（`turn-process`、`turn-tail`） | 长任务里唯一能回答"它现在在干什么、为什么慢、第几步了" | `ui-chat`（turn-process / turn-tail 定义与渲染）、`ui-conversation`（Turn/Step 坐标） | `useChat` | 一个多步骤任务能看出步骤推进与当前步骤 |
| **3** | **错误与重试**（`turn-error`、`retry`、`turn-max-tokens`） | 把"卡住"与"失败"区分开；没有它问题不可诊断 | `ui-chat`（turn-error / retry / turn-max-tokens 定义与渲染） | `useChat` | 构造一次失败与一次重试，界面能明确区分并显示原因 |
| **4** | **历史分页**（`loadOlder`） | 长会话的可用性边界；越晚做越容易返工（滚动锚点、虚拟列表、prepend 时的跳动） | `ui-conversation`（分页与会话骨架） | `loadOlder`（会话作用域） | 长会话滚到顶能拉取更早历史；前插时已有行不闪烁、不跳动 |
| **5** | **排队与中途引导**（`inbox` + queue 动作） | 这是 DSH 的差异化能力（`followup` / `steer`），不接就等于丢掉产品特性：用户无法在 agent 工作时补话或改方向 | `ui-conversation`（inbox/队列 + 输入机）、`ui-chat`（inbox 定义与渲染） | `inputActions` + `useChat`（inbox 节点） | 忙碌时补一条消息 → 出现在队列并可见；steer 生效 |
| **6** | **上下文压力与压缩**（`compaction`、`request-prompt`） | 长会话里用户唯一能理解"回答为什么变差/变了"的线索；也是排查成本的主要来源 | `ui-chat`（compaction / request-prompt / system-message 定义与渲染） | `useChat` | 触发一次压缩后界面有可见记录；上下文压力可见 |
| **7** | **命令与斜杠**（`command` 节点 + 命令面板） | 效率面：让高级操作不必点鼠标；也让产品能力（工具、模式、预设）可发现 | `ui-commands`（命令目录服务 + 面板）、`ui-input-trigger`（输入触发） | 保留 `ui-commands` 加载以复用其目录服务 + `useChat`（command 节点） | 输入 `/` 能列出命令并执行；执行结果在转写中可见 |

## 三、chat 节点 kind 对照（转写渲染的完整清单）

官方 chat target 折叠出的节点种类（供你按批实现，顺序见上表）：

| kind | 含义 | 本阶段顺序 |
|---|---|---|
| `assistant` | 助手输出（含流式增量） | 第一优先 #5（已完成最简版） |
| `message` | 用户/系统消息 | 与 #5 同批 |
| `tool` | 工具调用与结果 | 本阶段 #1 |
| `turn-process` | 轮次内的过程性输出 | #2 |
| `turn-tail` | 轮次收尾（总结/尾巴） | #2 |
| `turn-error` / `retry` / `turn-max-tokens` | 失败、重试、截断 | #3 |
| `inbox` | 排队与中途引导的可见行 | #5 |
| `compaction` / `request-prompt` / `system-message` | 压缩、请求头、系统消息 | #6 |
| `command` | 斜杠命令的调用与结果 | #7 |
| `fallback` | 未知节点的兜底渲染 | 与 #1 同批（必须有，否则新节点类型会直接消失） |

> **实现要点**：数据消费集中在一个适配层（把快照形状与你的渲染解耦），因为节点数据结构由官方包拥有，DSH 升级时可能需要跟着改。渲染器只读 `node.data` 与受限的 Location hook，不要扫描事件窗口（官方设计要求，也是性能底线）。

## 四、本阶段完成定义（DoD）

- [ ] 工具调用与结果可读（含参数与输出摘要）
- [ ] 多步骤任务能看出当前步骤与进度
- [ ] 失败、重试、截断三类情况界面可区分
- [ ] 长会话可向上翻页，前插不跳动
- [ ] 忙碌时可排队补话、可 steer
- [ ] 压缩/上下文压力有可见记录
- [ ] `/` 命令可列出并执行
- [ ] 未知节点类型有兜底渲染，不会静默消失
