DeepSeek Harness 原生桌面端技术分析

摘要

你不需要从零写一个 Electron 工程。当前仓库已经有桌面窗口、独立后端、通信协议、插件管理、安装包和更新机制。最适合你的起点是：先运行现有桌面版，再制作 Windows 未签名测试安装包，最后逐步加入企业品牌、智能体中心和账户权限。

01 桌面版实现原理

摘要

2.3 聊天 UI 在哪里

apps/desktop/renderer 只有启动和插件管理等壳页面。完整聊天界面的入口是 apps/web，具体侧栏、会话、工具卡片、设置等由 packages/client 插件贡献。Host 在加载页面时同时提供匹配版本的插件客户端资源。

所以，修改聊天气泡需要查 Client UI；修改“应用 → 插件管理”菜单需要查 Electron 主进程；增加 RAG 检索需要实现后端业务插件。不能把这三类修改混放在 main.ts 中。

3. 从双击到聊天页面

正式版的启动流程如下，开发版会跳过部分已签名资源与 Profile 管理步骤。

  1. Electron 读取 package.json 的 main: lib/main.js。
  2. 主进程申请单实例锁，重复启动时聚焦已有窗口，避免两个进程同时修改同一个桌面 Profile。
  3. 注册 dsh-app 协议，创建窗口。先显示本地 dsh-app://shell/startup.html，不必等待后端启动。
  4. 解析应用自带的 Node、pnpm、dsh 资源和 $DSH_HOME 数据路径。
  5. DesktopProjectManager.applyRelease() 准备或核对桌面 Profile，处理运行时版本变化和共享包链接。
  6. DesktopBackendController 通过 DesktopHostProcess 启动捆绑的上游 Node.js，执行 Host 的编译产物。
  7. Host 读取 Profile 的 bundle 和补丁，叠加桌面补丁，启动 Cordis 插件树。
  8. Host 检查 connection、clientModules、typertGateway 等服务已经存在，然后向主进程发送 ready。
  9. 主窗口加载 dsh-app://app/index.html；页面和插件资源来自 Host 对应的生产资源。
  10. 用户操作通过 API 与事件流到达 Agent/Session，模型输出逐步显示在页面上。

发生失败时，控制器记录错误并回到启动页。插件恢复和重置只在具备恢复条件的打包程序中提供。主进程退出时先等待后端停止，后端也会在父进程断开时释放请求与插件。

Windows 关闭最后一个窗口会退出应用；macOS 关闭窗口后应用可继续存在，通过应用激活重新创建窗口。相关实现位于 main.ts 和 backend-controller.ts。

4. 页面如何请求后端

4.1 自定义协议不是本地 HTTP 服务

聊天页面 fetch('/api/...')
  → Chromium 请求 dsh-app://app/api/...
  → Electron protocol.handle()
  → DesktopHostProcess 编成字节帧
  → 请求管道 fd 3
  → Desktop Host：连接处理器 / Typert 网关 / 资源处理器
  → 响应管道 fd 4
  → Electron 构造 Response
  → 聊天页面收到结果或持续读取输出

代码保留 Request、Response、状态码和 Fetch 的使用方式，但数据在桌面内部通过协议和管道传输。出现“HTTP 503”样式的错误消息不代表程序一定打开了 HTTP 端口。

默认组合不会监听 Web 服务端口。开发启动器另行打开主进程、Renderer、Host 的调试端口，默认分别是 9229、9222、9230。插件也可能自行创建网络服务，因此“默认桌面无 Web 监听”不等于所有扩展都无法监听网络。

4.2 数据分发

请求 Host 处理方式
/ 或 /index.html 读取 Web 构建首页，注入桌面 transport 与插件相关内容
/plugins/... 通过 clientModules.fetchBundle() 提供客户端插件 bundle
/api/... 通过共享 Fetch 处理器进入现有 API
/.dsh/remote-stream 调用 Typert 持续流接口，逐行输出 NDJSON
普通静态资源 从 Web 生产资源目录读取，检查路径是否越界

NDJSON 可以理解为“一行一个 JSON 对象”，用于持续送回事件。UI 逐步显示内容不必等待整个任务完成。Host 的原始字节传输不是给每段内容额外包一层 Base64。

4.3 协议、取消和背压

当前 Host 协议版本为 3。数据帧携带类型、流 ID 和长度，单个数据块最多 64 KiB；控制载荷有独立限制。一个子进程可以用不同流 ID 处理多个请求。取消信号会发送到 Host，并触发相关请求的 AbortController。

“背压”是消费速度较慢时让上游暂停写入，避免无限堆积。此实现有管道 drain 等待和暂停/恢复读取。协议错误或 Host 异常会让待处理请求失败，并通知桌面控制器。

Node IPC 通道只负责 ready、fatal、shutdown 等生命周期消息。它与 Electron 的 ipcRenderer/ipcMain 管理消息是两套用途不同的通信路径。Host 管道实现、Host 帧格式。

4.4 页面获得哪些权限

窗口开启 contextIsolation: true、sandbox: true、webSecurity: true，并关闭 nodeIntegration。普通聊天页面的 dshDesktop 只有协议标记；安装插件、重置配置等接口属于壳页面。主进程还检查管理消息是否来自 dsh-app://shell。

这意味着不能在聊天组件里随意 require('fs')，也不应该为了省事向页面暴露任意 exec()。新增原生能力时要增加明确、受限且校验调用来源的接口。此配置与 Electron 安全建议 一致；它不等于已经隔离了运行在 Node Host 里的全部第三方代码。

5. 桌面适配改变了哪些配置

桌面复用 base 和 web bundle，并通过 desktop.cordis.patch.yml 进行下列调整。

6. 插件安装与升级

6.1 核心包与扩展包

核心运行时是安装程序自带的，包括 dsh、私有 Host 和生产依赖。正式版 Profile 的 dependencies 记录外部插件的精确版本，dsh.profile.bundles 记录内置 bundle 和已启用的插件 bundle。

共享的第一方包由桌面程序链接到签名资源中真实的包目录，Windows 使用 junction。依赖这些包的外部插件必须正确声明 peer，不能再嵌套一套 Cordis 或 Harness 核心包。否则相同名字的类和服务可能来自不同模块实例。

普通业务依赖留在 Profile 内；桌面验证器会检查解析路径和 peer 版本范围。共享包校验。

6.2 一次安装事务

插件管理页提交包名和版本
  → 主进程校验参数和调用来源
  → 停止 Host
  → 持有 Profile 事务锁
  → 使用程序自带 pnpm 安装精确版本
  → 校验依赖、建立共享包链接、执行已允许的构建
  → 更新启用列表
  → 启动 Host 并加载界面

该实现直接修改当前 Profile。失败会保留已经发生的修改，供重试和修复；不是事务数据库式的自动回滚。不要在教程中承诺“装坏一个插件会自动还原”。

安装脚本先禁用依赖生命周期脚本，之后只执行 allowBuilds 已审查允许的构建。新增本地编译依赖不在清单内时会失败。这项限制与插件的业务操作权限不是一回事。

6.3 企业私有仓库的实际限制

当前插件管理接受 npm registry 包名及版本/标签，拒绝 file:、URL 和任意 pnpm 参数。管理器固定使用 https://registry.npmjs.org/，使用自己的 pnpm 目录和配置文件，并清理用户的 npm/pnpm 环境变量。

因此“在电脑上改一下全局 .npmrc，桌面就能安装公司私有包”不是当前实现保证的能力。企业需要增加经过验证的 registry 与凭据配置，或将审核后的插件加入企业发行版的构建输入。插件管理器。

7. 数据放在哪里

7.1 开发版

默认位置均在 apps/desktop/.desktop-build/development 下。

子目录 用途 处理原则
home 开发用会话、配置、凭据等 Harness 数据 有用数据要备份，不能当编译垃圾删除
project 自动重建的临时 npm 项目和依赖链接 不在这里长期编辑业务源码
electron-user-data 开发版 Chromium 缓存和浏览器状态 与 Harness 会话目录不同

DSH_HOME 可以替换开发 Harness home，但不会同时替换开发 npm project 和 Electron 浏览器数据目录。默认隔离是为了避免开发操作影响普通用户的 .dsh。

7.2 打包版

默认 $DSH_HOME 是 Windows 用户目录下的 .dsh，也可以被环境变量覆盖。$DSH_HOME/profiles/desktop 由桌面独占；$DSH_HOME/desktop/pnpm 保存桌面私有包管理器状态。应用安装目录的 resources 保存程序与运行时。

CLI 和 Desktop 共享受支持的产品数据，如会话、工作空间、设置和凭据；它们不共享可执行依赖、插件启用状态、锁文件或 node_modules。CLI 不能直接启动或修改保留的 desktop Profile。

“重置 Desktop”会删除这个 Profile 的配置与外部插件，并重新初始化。它不备份 Profile；也不等同于删除共享会话。清理前应确认操作对象和需要保留的数据。路径解析、Harness 默认 home。

8. 程序、运行时和更新的关系

安装包同时携带 Electron 外壳、匹配的 dsh、Desktop Host、上游 Node 和 pnpm。当前源码锁定的 Electron npm 版本是 44.0.0，打包脚本下载的上游 Node 是 24.17.0，pnpm 是 11.7.0；它们不是可以任意互换的运行组合。

desktop-runtime.json 记录 release、平台、架构、共享包及最终文件清单。打包期间校验完整性和版本匹配；启动时读取运行时信息并检查共享包记录。不要把它描述成“每次启动都会重新对所有文件做完整签名扫描”。

升级以整套桌面 release 为单位，不能只在用户机器里 pnpm update dsh。兼容升级主要刷新核心链接并保留外部插件；Node、平台或架构变化时，插件原生依赖可能需要按锁文件重装和重新构建。首次启动无核心 npm 安装，不代表以后的插件安装与运行环境变化永远不需要联网。

完整打包步骤见 04-安装包与发布教程。

9. 实现边界

该方案适合复用现有 Harness 的本地工具和 UI，且可以安装外部插件。代价是同时分发 Chromium、Node 和生产依赖，程序目录文件较多，发布验证也比单纯的静态网页复杂。

当前公开的目标命令覆盖 Windows x64、macOS arm64 和 macOS x64。配置中出现 Linux AppImage 或运行时下载代码支持 Linux，不代表已经具备受支持的 Linux 桌面发行流程；目标解析器会拒绝它。

它提供桌面执行环境，不提供企业账户隔离、中心化授权或自动的服务端数据同步。同一个 Host 中的第三方插件具有本地代码能力，不能把 Electron Renderer 沙箱当作第三方后端插件沙箱。你前面规划的智能体中心和多租户体系，应按 03-制作自己的桌面产品 接入。

步骤 2：安装或检查 Node.js

Node.js 是在电脑上运行 JavaScript 的工具。打开 Node.js 官方下载页，选择 Node 24 系列、Windows x64 安装程序，完成安装后重新打开 PowerShell。不要为了本教程追随网页上的最新主版本。

检查：

node --version
npm --version

成功条件：两个命令都输出版本号，不出现“无法识别”。当前仓库声明的 Node 范围是 ^22.19.0 || >=24.0.0；本次检查到的开发 Node 是 v24.18.0。打包后的 Host 使用脚本另行准备的 Node 24.17.0，与你电脑安装的开发 Node 不是同一个文件。

如果安装后仍找不到命令，先关闭所有终端再新开一个；再用 Get-Command node 查看 Windows 能否找到可执行文件。不要通过随意删改 PATH 来修复。

如果 npm --version 提示 npm.ps1 没有数字签名，改用 npm.cmd --version。本机确实遇到了这一情况，使用 npm.cmd 可输出 11.16.0；后面的全局 pnpm 安装命令也可对应使用 npm.cmd install --global pnpm@11.7.0。

步骤 3：安装匹配版本的 pnpm

pnpm 负责下载和组织仓库依赖。当前根目录 package.json 固定为 pnpm@11.7.0，使用这个版本，忽略“可以升级到新主版本”的提示。

已有 pnpm 时先检查：

pnpm --version

没有 pnpm 时，以下是需由操作者执行的环境安装步骤，本次没有重新安装全局工具：

npm install --global pnpm@11.7.0
pnpm --version

成功条件：输出 11.7.0。官方安装参考为 pnpm 安装文档，具体版本以仓库固定值为准。不要在这个项目根目录用 npm install 替代 pnpm install，以免产生另一套锁文件和依赖组织方式。

如果 PowerShell 提示 pnpm.ps1 被执行策略阻止，可以先尝试 pnpm.cmd --version。这是调用同一工具的 Windows 命令入口，不要求关闭系统脚本安全策略。

步骤 4：检查 Git，安装编辑器

Git 用来管理源码；构建还会读取 Git 提交信息。执行：

git --version

你已经有这个仓库，不需要重复克隆。编辑器可以使用 VS Code，也可以用现有代码编辑器。VS Code 与下面的 Visual Studio Build Tools 是两个不同工具：前者编辑代码，后者编译原生依赖。

步骤 5：为完整 Windows 打包准备 Python 和 C++ 工具链

依赖可能需要编译原生 Node 模块。准备 Python 3 和 Visual Studio Build Tools，并在安装器中选择“使用 C++ 的桌面开发”，包含 MSVC x64/x86 编译工具和 Windows SDK。此步骤由操作者完成，不是 pnpm 自动安装完整系统开发环境。Microsoft C++ Build Tools、node-gyp Windows 前置条件。

检查 Python：

python --version

如果电脑上只有 py，执行 py -3 --version。当原生构建找不到 Python 时，明确指定实际路径，例如：

$env:PYTHON = 'C:\Python311\python.exe'

这里的路径是示例，必须换成你电脑上存在的 python.exe。本次发现 Python 3.11.15；编译工具是否足够仍需以完整打包结果为准。不要仅凭 Python 有版本号就判断原生构建环境完整。

5. 配置模型与验证聊天

步骤 13：先用开发数据目录

默认开发 home 是：

D:\code\CYG\Github\deepseek-harness\apps\desktop\.desktop-build\development\home

它与通常的 C:\Users\你的用户名\.dsh 不同。因此你在普通 CLI 中保存过密钥，也不代表开发桌面版自动拥有同一份密钥。

如需自己指定一个独立目录，可以在启动终端中设置：

$env:DSH_HOME = 'D:\dsh-desktop-dev-data'

成功启动后，日志会打印实际 DSH_HOME。若已设置这个变量，后面的 .env 应放在你指定的目录，而不是默认 home。

步骤 14：把模型密钥放到 Harness home 的 .env

New-Item -ItemType Directory -Force -Path '.\apps\desktop\.desktop-build\development\home'
notepad '.\apps\desktop\.desktop-build\development\home\.env'

文件内容示例：

DEEPSEEK_API_KEY=替换为你自己的实际密钥

保存时确认文件名是 .env，不是 .env.txt。不要把真实密钥放进 DSH_CLIENT_* 变量、前端源码、截图或报告；这些客户端构建变量可以进入分发给用户的 JavaScript。

Host 会按继承环境、启动目录 .env、Harness home .env 的优先关系加载环境。桌面 Host 的启动目录是它的 Profile/开发 project，不能假定仓库根目录的 .env 总会被它读取。把密钥放进当前 Harness home 更明确。环境加载实现。

6. 修改后的日常操作

步骤 16：分清 dev、start 和 build

命令 用途 是否自动构建
pnpm run dev:desktop 第一次启动或修改源码后的稳妥入口 构建后启动
pnpm run start:desktop 已有匹配产物时快速重新打开 不构建；仍会重建开发项目链接
pnpm run build 构建仓库后端、客户端和 Web 产物 构建，不启动窗口
pnpm run build:desktop 只请求桌面壳包构建 不能替代全部 Web/Host 构建
pnpm run package:desktop:win:x64:unsigned 制作 Windows 测试安装包 自己执行完整发布准备

start:desktop 不会自动检测并补齐过时的所有产物。修改源代码后窗口没有变化，先完整退出，再运行 dev:desktop，不要在 lib 里直接改生成文件。

已经成功构建整个仓库，并且修改只涉及桌面壳时，可以执行：

pnpm run build:desktop
pnpm run start:desktop

步骤 18：正确停止应用

Windows 可通过应用菜单退出，或关闭最后一个窗口。等待终端返回命令提示符。应用正常退出会停止它管理的 Host。必要时再对你刚启动的终端按 Ctrl+C。

不要为了关这个应用而结束电脑上所有 node.exe，那可能终止编辑器和其他项目。若进程残留，按第 05 篇先核对进程路径和父子关系。

7. 调试和记录错误

步骤 19：知道三个调试端口分别看什么

默认端口 观察对象 环境变量
9229 Electron 主进程 DSH_DESKTOP_MAIN_INSPECT_PORT
9222 Chromium Renderer DSH_DESKTOP_RENDERER_DEBUG_PORT
9230 Node Host DSH_DESKTOP_HOST_INSPECT_PORT

这些不是聊天 Web 服务地址。端口被别的程序占用时，可在当前终端设置不同值，再启动：

$env:DSH_DESKTOP_MAIN_INSPECT_PORT = '19229'
$env:DSH_DESKTOP_RENDERER_DEBUG_PORT = '19222'
$env:DSH_DESKTOP_HOST_INSPECT_PORT = '19230'
pnpm run start:desktop

端口必须是 1 到 65535 的整数。不要把开发调试端口暴露到公网。

步骤 20：保留日志

遇到问题时，可以把下一次启动输出保存到文件：

pnpm run dev:desktop *> desktop-dev.log

另开一个 PowerShell 窗口，在仓库根目录查看：

Get-Content .\desktop-dev.log -Tail 60

日志重定向后，原终端可能很安静，但命令仍在运行。不要误以为它没有执行。分享日志前检查是否含本地路径、业务内容和敏感配置。本报告保存的日志不包含主动打印的模型密钥。

2. 第一个可见修改：窗口大小

先做一个影响范围小、容易观察的练习，验证你已理解“修改源文件 → 构建 → 重新运行”。

  1. 完全退出正在运行的开发桌面程序。
  2. 打开 apps/desktop/src/main.ts，搜索 function createWindow。
  3. 找到 BrowserWindow 配置中的 width: 1280 和 height: 840。
  4. 可将其改成 width: 1360 和 height: 900，保留 minWidth、minHeight 和 webPreferences 安全配置。
  5. 保存，然后在仓库根目录执行：
pnpm run build:desktop
pnpm run start:desktop
  1. 观察新窗口初始尺寸是否变化。练习完成后可以恢复原值，避免将练习改动混入正式产品。

这是明确的源码修改练习，不是本报告已经替你执行的产品变更。修改时不要碰 nodeIntegration、contextIsolation、sandbox 和 webSecurity，窗口尺寸与这些安全选项没有关系。

3.1 新手可以先修改安装器显示名

在 electron-builder.config.mjs 找到：

productName: 'DeepSeek Harness',

将这一项改成自己的测试名称，例如：

productName: 'QS 智能工作台',

再按第 04 篇重新打未签名包。此时安装器/应用名称可改变，但不代表聊天界面的官方 Logo、更新地址和数据 home 已经改变。源码开发时显示的应用名也不一定与打包安装后的名称完全一致，应分别验收。

当前配置没有一个通用的 DSH_DESKTOP_PRODUCT_NAME 环境变量。不要添加一个变量后，就假设程序会自动识别；要么修改现有配置值，要么正式增加并验证你自己的发行配置接口。

3.2 App ID 的操作

打包前在 PowerShell 设置：

$env:DSH_DESKTOP_APP_ID = 'com.example.qsdesktop'

这是格式示例，不要求你真的注册 example.com 才能做本地测试。公司正式发行应选用公司控制的命名，例如按公司域名反向组织。保持升级前后标识稳定；不要用同一标识发布互相不兼容的产品。

App ID 不是账号 ID，也不会自动建立独立租户。两个企业产品如果仍共用同一 $DSH_HOME，仍可能访问同一组本地产品数据。

3.3 客户端品牌的实际构建限制

普通开发构建支持从环境读取公开客户端标题，例如：

$env:DSH_CLIENT_TITLE = 'QS 智能工作台'
pnpm run dev:desktop

这是开发构建用法，未作为本次品牌改造实际执行。页面标题与 Logo 并不是同一个配置。

当前 package:desktop* 入口强制调用 build:official；官方构建会把标题和 build profile 固定为官方值。随后 release:pack --family dsh 还会验证产物具有官方构建记录。因此，单纯设置 DSH_CLIENT_TITLE 后直接运行现有打包命令，不足以制作完整的企业品牌发行版；仅把打包脚本中的 build:official 改成 build 也会碰到后续发布校验。

企业发行需要成套实现：自己的客户端构建 profile、对应的产物记录与校验、企业打包入口和目标配置。保留上游官方流程原有的校验语义，不用关闭校验来绕过品牌冲突。客户端构建策略、发布包校验。

3.4 替换 UI Logo 和名称

现有品牌插件通过 sidebar.brand.mark 和 sidebar.brand.name 两个 slot 注册侧栏品牌。企业品牌插件可以沿用这两个扩展点；单值 slot 应明确由谁占用，不能把官方与企业注册同时堆上去期待自动选择。

先阅读 ui-brand-official 实现 与 包清单。企业包需要 Host 入口、Client 入口、正确的 dsh.client 元数据、编译产物和类型依赖。若还要改会话首页图案，需要检查该组件自己声明的扩展位置，不能假设侧栏 Logo 会影响所有页面。

5. 企业插件如何进入桌面版

5.1 开发时

先在源码工作区开发和测试插件，将它纳入开发组合及声明的依赖。每次 start:desktop 会重建临时 project，因此不要把长期配置只改在 .desktop-build/development/project，否则下一次启动可能丢失。

开发桌面的插件菜单被禁用，后台也拒绝包变更。这个限制不是你安装失败；它是明确的开发模式行为。桌面包增删、依赖链接、事务修复应在打包的测试程序中验证。

5.2 用内置插件管理器安装

适用于已经发布到当前允许 registry 的 npm 包。包必须提供可激活的 bundle 元数据；仅有普通 Node 模块或普通 plugin 入口，不等于会自动加入 Profile。

操作顺序：启动打包程序 → 打开应用菜单的插件管理 → 输入实际包名和版本 → 等待程序停止 Host、安装及校验 → Host 重启 → 验证 UI 或业务能力。包名示例可以写成 @your-company/qs-agent-center@1.0.0，但只有真实存在且满足要求的包才能安装。

安装插件会运行本地代码，企业应使用审核过的包。这里的审核包括依赖与允许构建项，不能只验证页面是否出现。

5.3 企业私有插件的两条落地路径

随企业发行版内置。 将企业 bundle 纳入生产包闭包和发行校验，安装程序一次携带。优点是首次使用不必临时拉取业务核心包；代价是需要维护企业自己的构建输入和版本流程。

扩展桌面 registry 配置。 在 DesktopProjectManager 及构建准备中提供经过校验的 registry、作用域和凭据读取机制，并验证安装事务的隔离。用户全局 .npmrc 当前被隔离，不能直接拿来作为实现方案。要同时覆盖运行时安装和构建时准备，避免开发可装、打包失败。

不建议手工向已签名的 resources/dsh 复制文件，或让普通页面通过任意 shell 命令调用 pnpm；这会绕开当前的版本、依赖与完整性机制。

6. 智能体中心与多租户

结合你前面提出的“创建、配置、发布和使用智能体”，桌面端建议承担本地界面、可控的本机工具和会话执行；组织、授权、发布版本及共享知识库可以由企业服务集中管理。

桌面 UI：目录、创建配置、发布、聊天
  → 企业身份与业务插件
  → 企业服务：账户 / 组织 / 授权 / 智能体目录 / RAG / 微应用
  → 本地运行适配：固定智能体版本 + 独立 Session + 受限工具

这是建议新增的企业部署方案，不是当前桌面版默认连接了这样一个服务。

6.1 智能体与会话

中心保存智能体定义和已发布版本；点击使用后，为当前用户创建绑定该版本的 Session。不同用户使用同一个智能体配置，并不意味着共享一份上下文。

当前 Session 创建接口已有 agentPreset 字段，可作为运行组合接入点。但企业身份、业务空间和版本发布记录要由中心维护；恢复历史会话时仍需重新验证当前用户有权访问该会话和相关资源。

6.2 本地账户切换不能只清空页面

至少需要处理：停止或收拢原账户任务、断开原账户事件订阅、清理浏览器中的认证状态、切换会话可见范围、隔离文件缓存和模型/RAG缓存、重新绑定工具权限与凭据。

DSH_HOME 是进程级数据根，不能在共享 Host 中通过反复修改一个全局环境变量来实现请求级租户切换。更明确的方案是按账户/隔离域运行独立 Host，或为共享 Host 的所有持久化、API 和工具加入经过验证的身份上下文。

独立进程也不自动隔离操作系统文件权限。若智能体能执行终端命令，还需要与风险相匹配的 OS 账户、容器或沙箱限制。

6.3 哪一层执行授权

场景 必须执行授权的位置
是否能看到/使用某个智能体 智能体中心 API
是否能读别人历史会话 Session API 与事件流入口
RAG 能检索哪些文档 检索后端，在内容进入模型前过滤
能否修改/关闭工单 微应用后端，结合数据范围和业务状态
能否执行本机命令 工具与执行环境策略
能否安装第三方代码插件 桌面管理与企业分发政策

桌面安装包里不应内置一把全公司共用的长期模型管理员密钥。企业可通过服务端代理模型访问，或为用户提供受限凭据；具体方式由你选择的身份平台和模型接入决定。

7. 实施顺序与验收

  1. 原版开发运行。 验收：窗口、Host、静态资源、独立会话能工作。
  2. 原版未签名安装包。 验收：另一台干净 Windows 电脑无需系统 Node/pnpm 就能启动核心程序。
  3. 桌面品牌与企业发行配置。 验收：应用名、图标、内部标题、安装标识和更新域名一致。
  4. 一个最小企业插件。 验收：编译后可加载，Web/桌面均正常，不依赖监听 HTTP 路由。
  5. 账号与会话隔离。 验收：两个账户不能通过 API、事件订阅或本地缓存读到对方会话。
  6. 智能体中心。 验收：草稿、固定版本发布、授权使用和个人会话形成闭环。
  7. RAG 与微应用。 验收：检索、列表、导出、工具调用和业务写入执行一致的数据与操作权限。
  8. 正式签名和升级。 验收：已安装旧版本可升级，数据保留，插件兼容性检查有效，失败有明确恢复方式。

保持业务代码在独立企业仓库，桌面发行差异集中在少量有测试的适配与配置文件中。上游 API 仍处于 pre-stable 阶段，应固定使用的 Harness 版本，并安排升级兼容性验证。

Dev Note

本篇没有生成企业插件或修改品牌源码。企业构建 profile、私有 registry 支持、多租户与智能体中心均为需要实施的新增工作，不属于当前原版桌面能力。

1. 四类命令的区别

目标 命令 结果
打开开发窗口 pnpm run dev:desktop 运行源码构建产物，无安装器
生成 Windows 测试安装器 pnpm run package:desktop:win:x64:unsigned 未签名、无更新配置的测试产物
生成正式 Windows 安装器 pnpm run package:desktop:win:x64 要求发布身份、签名和更新配置
只准备运行时材料 pnpm run prepare:desktop 停在准备阶段，不调用安装器构建

prepare:desktop 不是打包前必须先跑的一步。package:desktop* 会自行完整准备；先 prepare 再 package 会重复工作。新手最容易选错的是把 package:desktop:win:x64:dir 当作免签名命令；:dir 只表示目录产物，它不会自动关闭签名要求。

2. Windows 未签名包逐步制作

步骤 1：确认前置条件

完成第 02 篇的 Node、pnpm、Python、C++ 工具链准备。确认使用 Windows x64、源码与锁文件一致，关闭会占用当前产物的桌面测试程序。在当前快照上，先解决上方提示的 fs-ext 检查阻塞。

步骤 2：进入仓库根目录

Set-Location 'D:\code\CYG\Github\deepseek-harness'

步骤 3：设置测试产品标识

$env:DSH_DESKTOP_APP_ID = 'com.example.qsdesktop'

标识必须满足反向域名格式。测试时可以使用该示例；正式产品换成企业自己的长期标识。此变量只在当前 PowerShell 及其子进程有效，所以设置和打包命令应在同一个终端执行。

不需要设置 DOWNLOAD_TEST_ORIGIN，也不需要为此命令设置 Windows 签名变量。未签名入口会清理签名凭据，并且不给最终应用生成自动更新配置。

步骤 4：执行完整打包

pnpm run package:desktop:win:x64:unsigned

首次需要准备生产依赖和运行时，耗时与网络、磁盘和缓存有关。本报告没有测得“成功安装器耗时”，因此不承诺固定分钟数。看到包数量增长和日志持续推进通常说明仍在执行；最终成功必须同时满足退出码为 0 且存在目标产物。

建议需要留证时执行下列等价的日志保存形式，不要同时运行两条打包任务：

pnpm run package:desktop:win:x64:unsigned *> desktop-package.log

另开终端查看：

Get-Content .\desktop-package.log -Tail 80

步骤 5：定位安装器

成功后，当前代码规定的未签名输出目录是：

D:\code\CYG\Github\deepseek-harness\apps\desktop\.desktop-build\targets\win-x64\unsigned-artifacts

列出顶层安装器候选：

Get-ChildItem '.\apps\desktop\.desktop-build\targets\win-x64\unsigned-artifacts' -Filter '*.exe'

文件名由 artifactName、版本、系统和架构展开。不要从更深层目录里随便找到一个 node.exe 就当成安装器。此处描述的是成功后的路径，本次没有产生可交付的安装器。

步骤 6：在测试电脑安装

把生成的安装器复制到测试电脑，双击打开，按向导选择安装目录并完成安装。配置使用 NSIS，oneClick: false 且允许修改安装目录，因此不是仅支持一键无交互安装。当前 builder 配置、NSIS 官方配置参考。

未签名包可能触发操作系统或企业终端防护的未知发布者提示。仅在确认这是自己的构建产物并符合测试环境要求时继续；不要为了安装测试包关闭全局系统防护。正式对外分发应采用签名路径。

步骤 7：验证最终用户不需要系统 Node/pnpm

最好在未安装开发工具的干净 Windows x64 测试机上验证。程序应从安装目录的资源中使用 Node 和 pnpm，而不是碰巧调用开发者电脑 PATH 中的运行时。

核心程序可以从本地完整资源启动；模型调用、远程数据和新增插件仍可能需要网络。不能把“首次不安装核心 npm 包”理解成“整套 AI 功能完全离线”。

额外安装包含原生构建步骤的插件时，还可能需要对应的编译条件和 allowBuilds 审查。“核心程序自带运行时”不承诺每一种第三方插件都能在没有开发工具的电脑上安装。

步骤 8：检查数据与卸载行为

确认会话保存于实际 Harness home，而不是应用安装目录。安装路径可变不应导致会话路径随意变化。测试创建会话、退出、重启恢复，再测试覆盖升级和卸载。卸载是否保留你需要的用户数据应通过安装器实测确认，本报告不推断未执行的卸载行为。

3. 打包脚本内部做什么

了解阶段名称后，就能看出错误发生在“下载”“编译”“组装”还是“安装器”。入口是 package-target.ts。

顺序 阶段 结果与检查
1 解析 win-x64 和 --unsigned 拒绝不支持的宿主/目标组合
2 build:official 编译所有需要的 Host、Client、Web、桌面产物并记录官方客户端构建信息
3 打包 dsh、私有 Host 和 vendored 包族 本地 npm tarball，避免把源码工作区链接直接分发给用户
4 打包 native/system 入口 准备与生产依赖对应的原生能力入口包
5 prepare:runtime 下载固定 Node，验证 SHA-256，准备固定 pnpm 并记录版本
6 prepare:packages 形成核心生产包集合与清单
7 prepare:dsh 在构建阶段安装生产依赖、实体化文件、过滤非运行文件、写运行时清单
8 原生载荷 smoke 与 Host smoke 在捆绑 Node 下检查原生依赖，并验证后端可启动和提供首页
9 electron-builder 把 Electron 壳和 extraResources 组装为 Windows 安装器

3.2 为什么安装包和解压后的大小不同

安装器压缩了资源，安装目录保留运行所需的实际文件。当前文件筛选会去掉类型声明、已识别的 source map、构建缓存及部分编译中间文件，同时保留运行 JavaScript、原生模块、DLL/EXE、WASM、许可证和必要资源。文件筛选策略。

不要通过删除“看起来很大”的 node_modules 或 DLL 来瘦身。任何裁剪都需要在最终打包资源中验证实际能力。

4. 用未打安装器的目录测试

2. 本次发现的三个具体问题

问题 A：开发依赖中残留两个失效 junction

实际错误为：

ENOENT: no such file or directory, stat
...node_modules\.pnpm\node_modules\@deepseek-ai\node-addon-landlock-run-linux-arm64

development-project.ts 会遍历工作区共享依赖，并对链接调用 realpathSync。本机发现两个 junction 指向不存在的 native/landlock-run/packages/linux-arm64、linux-x64。当前源码的原生能力目录是 native/system，这些属于本机安装树残留。

普通 pnpm install --frozen-lockfile 返回成功，但没有清除这两个链接。为继续验证，本次将已确认目标不存在的两个 junction 移到以下可恢复备份目录，没有删除它们，也没有删除任何目标目录：

D:\code\CYG\Github\deepseek-harness\node_modules\.desktop-analysis-stale-links-20260913

移动后启动流程越过开发项目准备，进入 Electron 下载阶段。这只证明该阻塞被解除，不证明后续窗口成功。

你的电脑出现类似错误时，先核对链接类型和目标是否确实不存在。不要复制一个“递归删除所有 node_modules”的命令，不要删除仍有有效目标的 junction。新手可以把路径和错误交给开发人员，按限定范围备份处理。

问题 B：Electron 压缩包下载未完成

修复链接后，启动日志停在 Downloading Electron binary...。本次没有拿到可启动的 Electron 二进制，也没有获得真实桌面窗口截图。

对官方 Windows x64 ZIP 地址的 HEAD 探测返回 200，但实际下载返回 Received an unexpected EOF or 0 bytes from the transport stream.。因此“网页能打开”或“HEAD 200”不等于大文件下载已完成。持续无进展的本次 Electron 下载子进程已停止；日志末尾的安装失败提示包含这次主动停止的影响，不能全部当成 Electron 自行抛出的根因。

建议在公司网络中检查 GitHub Release 资产下载、HTTPS 代理和大文件传输策略。使用经过批准的网络路径后，让当前锁定版本的 Electron 安装脚本重新下载并校验。不要改用随机网站的同名 .exe，也不要将任意旧版本 Electron 路径强行替换进来。

问题 C：打包 smoke 检查了不存在的 fs-ext

实际命令：

$env:DSH_DESKTOP_APP_ID = 'com.example.qsdesktop'
pnpm run package:desktop:win:x64:unsigned

失败位置：

desktop native payload smoke failed
Error: Cannot find module 'fs-ext'
at checkFsExt (.../runtime-payload-smoke.mjs:69:17)

证据链如下：

  1. prepare-dsh.ts 在生产依赖准备后调用原生载荷检查脚本。
  2. runtime-payload-smoke.mjs 的 checkFsExt() 无条件 requireRuntime('fs-ext')。
  3. 本次扫描 apps/* 和 packages/*/* 包清单的 dependencies、optionalDependencies 和 peerDependencies，没有发现生产依赖声明 fs-ext；不要将名字相似的 fs-extra 当成同一个包。
  4. 当前 JSONL 持久化包依赖 @deepseek-ai/node-addon-system 与 koffi，POSIX lease 导入的是 @deepseek-ai/node-addon-system/flock。
  5. 打包在此退出，后续 Koffi、Sharp、HTML、PTY 及完整 Host smoke 没有因为“检查脚本已开始”就自动被证明通过。

据此判断，桌面载荷检查与当前生产依赖发生了不一致，检查脚本保留旧依赖要求的可能性很高。修复需要由维护人员确认真实运行需求；不是让最终用户额外安装一个全局 fs-ext。本次仅分析和记录，未修改该脚本。

启动页的恢复按钮应该怎么用

“重启”用于重新启动应用；“禁用插件”用于排除外部插件影响；“重置 Desktop”会清除桌面 Profile 的配置与外部插件。恢复选项受打包资源和当前错误状态限制，开发模式可能只允许重启。

重置不是通用修复按钮。先备份需要的 Profile 配置；不要为网络下载错误或源码编译错误重置用户数据。共享 Harness 会话与 .env 的归属见第 01 篇。
