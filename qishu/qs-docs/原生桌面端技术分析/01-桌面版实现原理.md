# 01 桌面版实现原理

## 摘要

当前桌面版的主要结构是“Electron 外壳 + Chromium 中的 Web UI + 独立上游 Node.js 运行的 Harness”。Electron 管窗口和桌面操作；Harness 管智能体、会话、工具及插件；Web UI 负责展示。两个目录配合工作，还依赖整个仓库的能力包，不能只复制这两个文件夹就得到完整产品。

## 1. 先理解基本概念

| 名词 | 初学者可以怎样理解 | 在本项目中的具体位置 |
|---|---|---|
| Electron | 用 Web 技术做可安装桌面程序的框架 | 创建窗口、原生菜单、更新入口 |
| Main 主进程 | 桌面程序的管理进程 | `apps/desktop/src/main.ts` |
| Renderer 渲染进程 | 执行页面、显示按钮和聊天内容的进程 | Chromium 中的 Harness Web UI |
| Preload 预加载脚本 | 在页面加载前提供经过限制的桌面接口 | `preload-app.ts`、`preload.ts` |
| Desktop Host | 真正执行 Harness 后端的独立子进程 | `apps/desktop-host/src/index.ts` |
| Node.js | 在浏览器外执行 JavaScript 的运行时 | 为后端和工具提供运行环境 |
| Cordis 插件 | 向 Harness 提供能力或界面的模块 | 各个 `packages/` 能力包 |
| Profile | 一组启用的插件包和配置层 | 正式版的 `$DSH_HOME/profiles/desktop` |
| Bundle | 可以加入 Profile 的插件装配包 | 内置 base/web bundle 和企业扩展 bundle |
| IPC | 进程之间传递消息的方式 | Electron 页面管理消息、Host 生命周期消息 |
| 构建 | 把源码转换成程序能直接使用的产物 | TypeScript 编译、tsdown 和 Vite |
| 打包 | 把程序及依赖组装为可交付目录或安装包 | electron-builder、NSIS |

Electron 的主进程、渲染进程和 Preload 概念可参照 [Electron 官方进程说明](https://www.electronjs.org/docs/latest/tutorial/process-model)。下面关于额外 Node 子进程和数据通信的细节来自本仓库源码，而非所有 Electron 应用都采用的默认结构。

## 2. 两个目录与前端的关系

```text
用户的 Windows 电脑
│
├─ Electron 主进程：apps/desktop
│  ├─ 创建聊天窗口、启动页、插件管理窗口
│  ├─ 管理 Host 启停、Profile、安装与更新
│  └─ 注册 dsh-app:// 自定义协议
│
├─ Chromium 渲染进程
│  ├─ 壳页面：apps/desktop/renderer
│  └─ 聊天页面：apps/web + packages/client 的插件
│
└─ 独立 Node.js 子进程：apps/desktop-host
   ├─ Cordis + base/web bundle + 桌面补丁 + 业务插件
   ├─ Agent、Session、模型、工具、持久化
   └─ API、持续事件流、前端资源处理
```

这张图只画业务相关的主要执行部分。Electron 自身还可能启动 GPU、工具等辅助进程，因此任务管理器里不一定只有三个进程。

### 2.2 `apps/desktop-host` 为什么文件少

它的职责是装配和转发，智能体业务实现仍由 Harness 包承担。

| 文件 | 作用 |
|---|---|
| `src/index.ts` | 读取 Profile、应用桌面补丁、启动 Cordis、处理 API/资源/事件流、停止后端 |
| `src/wire.ts` | 子进程端字节帧协议和消息校验 |
| `config/desktop.cordis.patch.yml` | 禁用 Web 网络与浏览器启动功能，换上桌面适配 |
| `package.json` | 声明 Host 依赖的包、版本及打包文件 |
| `tsconfig.json`、`tsdown.config.ts` | 编译 TypeScript 并生成 Host JavaScript |

Host 是私有应用组件，不能当成一个普通业务插件直接安装。直接执行它的源码也不是教程入口：它需要父进程准备目录、两个数据管道和 Node IPC 通道。根目录桌面脚本负责启动受管理的 Profile。当前架构文档明确描述了这条私有桌面装配路径。[Desktop Host](/D:/code/CYG/Github/deepseek-harness/apps/desktop-host/src/index.ts)、[架构中的桌面应用](/D:/code/CYG/Github/deepseek-harness/docs/architecture.md)。

### 2.3 聊天 UI 在哪里

`apps/desktop/renderer` 只有启动和插件管理等壳页面。完整聊天界面的入口是 `apps/web`，具体侧栏、会话、工具卡片、设置等由 `packages/client` 插件贡献。Host 在加载页面时同时提供匹配版本的插件客户端资源。

所以，修改聊天气泡需要查 Client UI；修改“应用 → 插件管理”菜单需要查 Electron 主进程；增加 RAG 检索需要实现后端业务插件。不能把这三类修改混放在 `main.ts` 中。

## 3. 从双击到聊天页面

正式版的启动流程如下，开发版会跳过部分已签名资源与 Profile 管理步骤。

1. Electron 读取 `package.json` 的 `main: lib/main.js`。
2. 主进程申请单实例锁，重复启动时聚焦已有窗口，避免两个进程同时修改同一个桌面 Profile。
3. 注册 `dsh-app` 协议，创建窗口。先显示本地 `dsh-app://shell/startup.html`，不必等待后端启动。
4. 解析应用自带的 Node、pnpm、dsh 资源和 `$DSH_HOME` 数据路径。
5. `DesktopProjectManager.applyRelease()` 准备或核对桌面 Profile，处理运行时版本变化和共享包链接。
6. `DesktopBackendController` 通过 `DesktopHostProcess` 启动捆绑的上游 Node.js，执行 Host 的编译产物。
7. Host 读取 Profile 的 bundle 和补丁，叠加桌面补丁，启动 Cordis 插件树。
8. Host 检查 `connection`、`clientModules`、`typertGateway` 等服务已经存在，然后向主进程发送 `ready`。
9. 主窗口加载 `dsh-app://app/index.html`；页面和插件资源来自 Host 对应的生产资源。
10. 用户操作通过 API 与事件流到达 Agent/Session，模型输出逐步显示在页面上。

发生失败时，控制器记录错误并回到启动页。插件恢复和重置只在具备恢复条件的打包程序中提供。主进程退出时先等待后端停止，后端也会在父进程断开时释放请求与插件。

Windows 关闭最后一个窗口会退出应用；macOS 关闭窗口后应用可继续存在，通过应用激活重新创建窗口。相关实现位于 [main.ts](/D:/code/CYG/Github/deepseek-harness/apps/desktop/src/main.ts) 和 [backend-controller.ts](/D:/code/CYG/Github/deepseek-harness/apps/desktop/src/backend-controller.ts)。

<a id="通信"></a>
## 4. 页面如何请求后端

### 4.1 自定义协议不是本地 HTTP 服务

```text
聊天页面 fetch('/api/...')
  → Chromium 请求 dsh-app://app/api/...
  → Electron protocol.handle()
  → DesktopHostProcess 编成字节帧
  → 请求管道 fd 3
  → Desktop Host：连接处理器 / Typert 网关 / 资源处理器
  → 响应管道 fd 4
  → Electron 构造 Response
  → 聊天页面收到结果或持续读取输出
```

代码保留 `Request`、`Response`、状态码和 Fetch 的使用方式，但数据在桌面内部通过协议和管道传输。出现“HTTP 503”样式的错误消息不代表程序一定打开了 HTTP 端口。

默认组合不会监听 Web 服务端口。开发启动器另行打开主进程、Renderer、Host 的调试端口，默认分别是 9229、9222、9230。插件也可能自行创建网络服务，因此“默认桌面无 Web 监听”不等于所有扩展都无法监听网络。

### 4.2 数据分发

| 请求 | Host 处理方式 |
|---|---|
| `/` 或 `/index.html` | 读取 Web 构建首页，注入桌面 transport 与插件相关内容 |
| `/plugins/...` | 通过 `clientModules.fetchBundle()` 提供客户端插件 bundle |
| `/api/...` | 通过共享 Fetch 处理器进入现有 API |
| `/.dsh/remote-stream` | 调用 Typert 持续流接口，逐行输出 NDJSON |
| 普通静态资源 | 从 Web 生产资源目录读取，检查路径是否越界 |

NDJSON 可以理解为“一行一个 JSON 对象”，用于持续送回事件。UI 逐步显示内容不必等待整个任务完成。Host 的原始字节传输不是给每段内容额外包一层 Base64。

### 4.3 协议、取消和背压

当前 Host 协议版本为 3。数据帧携带类型、流 ID 和长度，单个数据块最多 64 KiB；控制载荷有独立限制。一个子进程可以用不同流 ID 处理多个请求。取消信号会发送到 Host，并触发相关请求的 `AbortController`。

“背压”是消费速度较慢时让上游暂停写入，避免无限堆积。此实现有管道 `drain` 等待和暂停/恢复读取。协议错误或 Host 异常会让待处理请求失败，并通知桌面控制器。

Node IPC 通道只负责 `ready`、`fatal`、`shutdown` 等生命周期消息。它与 Electron 的 `ipcRenderer/ipcMain` 管理消息是两套用途不同的通信路径。[Host 管道实现](/D:/code/CYG/Github/deepseek-harness/apps/desktop/src/host-process.ts)、[Host 帧格式](/D:/code/CYG/Github/deepseek-harness/apps/desktop-host/src/wire.ts)。

### 4.4 页面获得哪些权限

窗口开启 `contextIsolation: true`、`sandbox: true`、`webSecurity: true`，并关闭 `nodeIntegration`。普通聊天页面的 `dshDesktop` 只有协议标记；安装插件、重置配置等接口属于壳页面。主进程还检查管理消息是否来自 `dsh-app://shell`。

这意味着不能在聊天组件里随意 `require('fs')`，也不应该为了省事向页面暴露任意 `exec()`。新增原生能力时要增加明确、受限且校验调用来源的接口。此配置与 [Electron 安全建议](https://www.electronjs.org/docs/latest/tutorial/security) 一致；它不等于已经隔离了运行在 Node Host 里的全部第三方代码。

## 5. 桌面适配改变了哪些配置

桌面复用 base 和 web bundle，并通过 [desktop.cordis.patch.yml](/D:/code/CYG/Github/deepseek-harness/apps/desktop-host/config/desktop.cordis.patch.yml) 进行下列调整。

| 配置行 | 调整及目的 |
|---|---|
| `web-startup`、`webserver`、`web-runtime` | 禁用浏览器启动和 Web 监听相关组合 |
| `client-hmr` | 禁用 Web HMR，因此桌面开发脚本不是保存即完整热更新的服务器 |
| `open-in-app`、`ui-open-in-app` | 禁用依赖 HTTP 路由的 Open In 功能 |
| `directory-picker` | 禁用浏览式目录选择器 |
| `connection` | 保留凭据相关依赖，使用桌面共享请求处理路径 |
| `directory-picker-native`、`ui-directory-picker-native` | 安装原生目录选择能力和客户端消费者 |

特别注意：本仓库的原生目录选择器是 Harness 能力插件。Windows 实现由 Host 启动子进程调用原生 `IFileOpenDialog`，并非简单地由 `main.ts` 调用 `dialog.showOpenDialog()`。[原生目录选择插件](/D:/code/CYG/Github/deepseek-harness/packages/host/directory-picker-native/src/index.ts)。

配置层也有差异：Host 从 Profile 的 bundle 层、Profile 补丁和桌面补丁装配，再为 Preset 根目录追加适配。不要假设 Web/CLI 的每一种全局补丁在 Desktop 中都有相同加载顺序。

<a id="插件"></a>
## 6. 插件安装与升级

### 6.1 核心包与扩展包

核心运行时是安装程序自带的，包括 dsh、私有 Host 和生产依赖。正式版 Profile 的 `dependencies` 记录外部插件的精确版本，`dsh.profile.bundles` 记录内置 bundle 和已启用的插件 bundle。

共享的第一方包由桌面程序链接到签名资源中真实的包目录，Windows 使用 junction。依赖这些包的外部插件必须正确声明 peer，不能再嵌套一套 Cordis 或 Harness 核心包。否则相同名字的类和服务可能来自不同模块实例。

普通业务依赖留在 Profile 内；桌面验证器会检查解析路径和 peer 版本范围。[共享包校验](/D:/code/CYG/Github/deepseek-harness/apps/desktop/src/profile-packages.ts)。

### 6.2 一次安装事务

```text
插件管理页提交包名和版本
  → 主进程校验参数和调用来源
  → 停止 Host
  → 持有 Profile 事务锁
  → 使用程序自带 pnpm 安装精确版本
  → 校验依赖、建立共享包链接、执行已允许的构建
  → 更新启用列表
  → 启动 Host 并加载界面
```

该实现直接修改当前 Profile。失败会保留已经发生的修改，供重试和修复；不是事务数据库式的自动回滚。不要在教程中承诺“装坏一个插件会自动还原”。

安装脚本先禁用依赖生命周期脚本，之后只执行 `allowBuilds` 已审查允许的构建。新增本地编译依赖不在清单内时会失败。这项限制与插件的业务操作权限不是一回事。

### 6.3 企业私有仓库的实际限制

当前插件管理接受 npm registry 包名及版本/标签，拒绝 `file:`、URL 和任意 pnpm 参数。管理器固定使用 `https://registry.npmjs.org/`，使用自己的 pnpm 目录和配置文件，并清理用户的 npm/pnpm 环境变量。

因此“在电脑上改一下全局 `.npmrc`，桌面就能安装公司私有包”不是当前实现保证的能力。企业需要增加经过验证的 registry 与凭据配置，或将审核后的插件加入企业发行版的构建输入。[插件管理器](/D:/code/CYG/Github/deepseek-harness/apps/desktop/src/project-manager.ts)。

<a id="数据"></a>
## 7. 数据放在哪里

### 7.1 开发版

默认位置均在 `apps/desktop/.desktop-build/development` 下。

| 子目录 | 用途 | 处理原则 |
|---|---|---|
| `home` | 开发用会话、配置、凭据等 Harness 数据 | 有用数据要备份，不能当编译垃圾删除 |
| `project` | 自动重建的临时 npm 项目和依赖链接 | 不在这里长期编辑业务源码 |
| `electron-user-data` | 开发版 Chromium 缓存和浏览器状态 | 与 Harness 会话目录不同 |

`DSH_HOME` 可以替换开发 Harness home，但不会同时替换开发 npm project 和 Electron 浏览器数据目录。默认隔离是为了避免开发操作影响普通用户的 `.dsh`。

### 7.2 打包版

默认 `$DSH_HOME` 是 Windows 用户目录下的 `.dsh`，也可以被环境变量覆盖。`$DSH_HOME/profiles/desktop` 由桌面独占；`$DSH_HOME/desktop/pnpm` 保存桌面私有包管理器状态。应用安装目录的 `resources` 保存程序与运行时。

CLI 和 Desktop 共享受支持的产品数据，如会话、工作空间、设置和凭据；它们不共享可执行依赖、插件启用状态、锁文件或 `node_modules`。CLI 不能直接启动或修改保留的 desktop Profile。

“重置 Desktop”会删除这个 Profile 的配置与外部插件，并重新初始化。它不备份 Profile；也不等同于删除共享会话。清理前应确认操作对象和需要保留的数据。[路径解析](/D:/code/CYG/Github/deepseek-harness/apps/desktop/src/paths.ts)、[Harness 默认 home](/D:/code/CYG/Github/deepseek-harness/packages/util/home-paths/src/index.ts)。

<a id="发布"></a>
## 8. 程序、运行时和更新的关系

安装包同时携带 Electron 外壳、匹配的 dsh、Desktop Host、上游 Node 和 pnpm。当前源码锁定的 Electron npm 版本是 44.0.0，打包脚本下载的上游 Node 是 24.17.0，pnpm 是 11.7.0；它们不是可以任意互换的运行组合。

`desktop-runtime.json` 记录 release、平台、架构、共享包及最终文件清单。打包期间校验完整性和版本匹配；启动时读取运行时信息并检查共享包记录。不要把它描述成“每次启动都会重新对所有文件做完整签名扫描”。

升级以整套桌面 release 为单位，不能只在用户机器里 `pnpm update dsh`。兼容升级主要刷新核心链接并保留外部插件；Node、平台或架构变化时，插件原生依赖可能需要按锁文件重装和重新构建。首次启动无核心 npm 安装，不代表以后的插件安装与运行环境变化永远不需要联网。

完整打包步骤见 [04-安装包与发布教程](04-安装包与发布教程.md)。

<a id="边界"></a>
## 9. 实现边界

该方案适合复用现有 Harness 的本地工具和 UI，且可以安装外部插件。代价是同时分发 Chromium、Node 和生产依赖，程序目录文件较多，发布验证也比单纯的静态网页复杂。

当前公开的目标命令覆盖 Windows x64、macOS arm64 和 macOS x64。配置中出现 Linux AppImage 或运行时下载代码支持 Linux，不代表已经具备受支持的 Linux 桌面发行流程；目标解析器会拒绝它。

它提供桌面执行环境，不提供企业账户隔离、中心化授权或自动的服务端数据同步。同一个 Host 中的第三方插件具有本地代码能力，不能把 Electron Renderer 沙箱当作第三方后端插件沙箱。你前面规划的智能体中心和多租户体系，应按 [03-制作自己的桌面产品](03-制作自己的桌面产品.md) 接入。
