# 05 故障排查与验收

## 摘要

遇到错误时，先确定失败阶段，再处理该阶段的原因。当前快照实测存在开发依赖残留、Electron 二进制下载未完成，以及打包载荷检查依赖 `fs-ext` 的问题。本篇将本机证据与一般排查方法分开，避免你把源码问题误当成操作错误。

<a id="定位"></a>
## 1. 按最后的错误定位

```text
命令无法识别
  → Node / pnpm / PATH / PowerShell 入口
依赖安装失败
  → 锁文件 / 下载网络 / 原生构建工具
tsc 或 tsdown 报错
  → 源码编译 / 依赖或版本不一致
development project 报 ENOENT
  → 工作区依赖链接 / 编译产物
Downloading Electron binary 长时间不结束
  → Electron 压缩包下载 / 缓存 / 网络
窗口出现但停在启动页
  → Host / Profile / 插件 / 原生模块
聊天页正常但模型报错
  → 模型凭据 / Provider / 出站网络
prepare:dsh 或 payload smoke 报错
  → 打包生产依赖 / 筛选策略 / 检查脚本
electron-builder 或 SignTool 报错
  → 安装器 / 目标平台 / 签名环境
```

不要只复制终端最后一行 `ELIFECYCLE` 给别人。它表示上层脚本失败，真正的原因通常在前面的第一条 `Error`、模块缺失或编译诊断中。

<a id="实测"></a>
## 2. 本次发现的三个具体问题

### 问题 A：开发依赖中残留两个失效 junction

实际错误为：

```text
ENOENT: no such file or directory, stat
...node_modules\.pnpm\node_modules\@deepseek-ai\node-addon-landlock-run-linux-arm64
```

`development-project.ts` 会遍历工作区共享依赖，并对链接调用 `realpathSync`。本机发现两个 junction 指向不存在的 `native/landlock-run/packages/linux-arm64`、`linux-x64`。当前源码的原生能力目录是 `native/system`，这些属于本机安装树残留。

普通 `pnpm install --frozen-lockfile` 返回成功，但没有清除这两个链接。为继续验证，本次将已确认目标不存在的两个 junction 移到以下可恢复备份目录，没有删除它们，也没有删除任何目标目录：

```text
D:\code\CYG\Github\deepseek-harness\node_modules\.desktop-analysis-stale-links-20260913
```

移动后启动流程越过开发项目准备，进入 Electron 下载阶段。这只证明该阻塞被解除，不证明后续窗口成功。

你的电脑出现类似错误时，先核对链接类型和目标是否确实不存在。不要复制一个“递归删除所有 node_modules”的命令，不要删除仍有有效目标的 junction。新手可以把路径和错误交给开发人员，按限定范围备份处理。

### 问题 B：Electron 压缩包下载未完成

修复链接后，启动日志停在 `Downloading Electron binary...`。本次没有拿到可启动的 Electron 二进制，也没有获得真实桌面窗口截图。

对官方 Windows x64 ZIP 地址的 HEAD 探测返回 200，但实际下载返回 `Received an unexpected EOF or 0 bytes from the transport stream.`。因此“网页能打开”或“HEAD 200”不等于大文件下载已完成。持续无进展的本次 Electron 下载子进程已停止；日志末尾的安装失败提示包含这次主动停止的影响，不能全部当成 Electron 自行抛出的根因。

建议在公司网络中检查 GitHub Release 资产下载、HTTPS 代理和大文件传输策略。使用经过批准的网络路径后，让当前锁定版本的 Electron 安装脚本重新下载并校验。不要改用随机网站的同名 `.exe`，也不要将任意旧版本 Electron 路径强行替换进来。

### 问题 C：打包 smoke 检查了不存在的 `fs-ext`

实际命令：

```powershell
$env:DSH_DESKTOP_APP_ID = 'com.example.qsdesktop'
pnpm run package:desktop:win:x64:unsigned
```

失败位置：

```text
desktop native payload smoke failed
Error: Cannot find module 'fs-ext'
at checkFsExt (.../runtime-payload-smoke.mjs:69:17)
```

证据链如下：

1. [prepare-dsh.ts](/D:/code/CYG/Github/deepseek-harness/apps/desktop/scripts/prepare-dsh.ts) 在生产依赖准备后调用原生载荷检查脚本。
2. [runtime-payload-smoke.mjs](/D:/code/CYG/Github/deepseek-harness/apps/desktop/tests/fixtures/runtime-payload-smoke.mjs) 的 `checkFsExt()` 无条件 `requireRuntime('fs-ext')`。
3. 本次扫描 `apps/*` 和 `packages/*/*` 包清单的 `dependencies`、`optionalDependencies` 和 `peerDependencies`，没有发现生产依赖声明 `fs-ext`；不要将名字相似的 `fs-extra` 当成同一个包。
4. 当前 JSONL 持久化包依赖 `@deepseek-ai/node-addon-system` 与 `koffi`，POSIX lease 导入的是 `@deepseek-ai/node-addon-system/flock`。
5. 打包在此退出，后续 Koffi、Sharp、HTML、PTY 及完整 Host smoke 没有因为“检查脚本已开始”就自动被证明通过。

据此判断，桌面载荷检查与当前生产依赖发生了不一致，检查脚本保留旧依赖要求的可能性很高。修复需要由维护人员确认真实运行需求；不是让最终用户额外安装一个全局 `fs-ext`。本次仅分析和记录，未修改该脚本。

<a id="常见"></a>
## 3. 常见问题处理

| 现象 | 先检查什么 | 处理方式 |
|---|---|---|
| `pnpm` 无法识别 | Node/npm/pnpm 是否安装，终端是否重开 | 按第 02 篇安装固定版本 |
| `pnpm.ps1` 被执行策略阻止 | 是否可以调用 `pnpm.cmd` | 使用命令入口，不关闭全局安全策略 |
| Unsupported platform 警告 | 最终退出码是否为 0 | 区分非本机原生包的警告与真实失败 |
| `missing built artifact` | 是否跳过第一次构建 | 先运行 `dev:desktop` |
| 失效 workspace 链接 | 链接目标是否仍存在 | 安装依赖后核对残留，仅处理确认失效的链接 |
| `node-gyp`/Python/MSVC 错误 | Python 路径与 C++ workload | 按原生模块前置条件补齐工具 |
| 窗口尺寸改了却不变 | 是否改的是 `src`，是否退出旧实例 | 构建壳并重新启动 |
| 聊天页面改了却不变 | 是否只构建了桌面壳 | 使用完整 `dev:desktop` |
| 桌面内 `require` 不存在 | 是否在 Renderer 中直接调用 Node API | 通过现有能力或受限 Preload 接口实现 |
| 插件菜单不可用 | 是否处于源码开发模式 | 使用打包测试程序验证包安装 |
| `plugin package changes require a packaged application` | 调用了开发模式禁用的管理操作 | 不要删掉保护判断来测试 |
| 私有包安装失败 | registry 是否固定、全局 npmrc 是否被隔离 | 增加企业 registry/凭据支持或随发行版内置 |
| peer version 或重复核心包错误 | 企业插件是否带了自己的 Cordis/Harness 核心副本 | 正确声明 peer 并匹配发行版本 |
| 安装插件后启动失败 | 插件代码、依赖、构建许可和 Host 错误 | 按启动页修复；当前机制不自动回滚 |
| `backend unavailable` / 503 | Host 是否 ready 或已退出 | 查看主进程和 Host 错误，不要先排查浏览器端口 |
| 模型鉴权失败 | 当前 `DSH_HOME`、实际 Provider、环境继承 | 修正当前 home 的凭据后重启 |
| Web “Open In” 按钮不见 | 桌面补丁禁用了依赖 HTTP 的功能 | 这是当前组合限制，新增适配需另做实现 |
| `DSH_DESKTOP_APP_ID must be set` | 是否在同一终端设置 appId | 设置反向域名格式后重新打包 |
| 未准备证书却要求签名 | 是否选了正式命令或 `:dir` | 本地测试使用明确的 `:unsigned` 路径 |
| `DOWNLOAD_TEST_ORIGIN` 缺失 | 是否正在正式打包且默认 test 环境 | 配置自己的 HTTPS origin |
| 更新地址指向上游 | 是否设置了 `production` | 企业发行需要改自有更新策略 |
| Linux 打包被拒绝 | 是否误把配置中的 AppImage 当成完整支持 | 使用当前固定目标，Linux 需单独建设验证链 |
| 点击程序出现另一个窗口/聚焦旧窗口 | 单实例和旧进程是否仍在 | 正常退出旧实例后再测试 |

### 启动页的恢复按钮应该怎么用

“重启”用于重新启动应用；“禁用插件”用于排除外部插件影响；“重置 Desktop”会清除桌面 Profile 的配置与外部插件。恢复选项受打包资源和当前错误状态限制，开发模式可能只允许重启。

重置不是通用修复按钮。先备份需要的 Profile 配置；不要为网络下载错误或源码编译错误重置用户数据。共享 Harness 会话与 `.env` 的归属见第 01 篇。

<a id="修复"></a>
## 4. 给开发人员的修复步骤

下面是针对本次打包阻塞的建议实施单，不是已经执行的补丁。

1. 确认当前发布依赖闭包是否仍有任何生产功能使用 `fs-ext`。本次应用与能力包清单扫描为空，但维护人员仍应核对真实运行路径。
2. 若已无生产用途，把原生载荷 smoke 更新为当前实际随包分发和执行的能力，不再强制检查未分发的旧包。
3. 若确有用途，由真正使用该包的生产模块声明依赖，并验证它在目标 Node/Windows 下的支持；不要仅为了让检查通过而塞一个无业务用途的包。
4. 同步检查 `project-manager.ts` 的 `allowBuilds`、`runtime-file-policy.ts` 和相关 fixture，决定哪些通用兼容筛选可以保留、哪些要求已经失效。不要一次删除全部原生检查。
5. 增加能够复现“生产依赖不存在但 smoke 仍强制加载”的有效用例，并验证新检查实际覆盖随包能力。遵循仓库关于原生子进程测试和 Agent Note 的要求。
6. 重新执行 Windows 未签名完整打包；确认原生载荷检查、Host smoke 和资源完整性检查均通过后，才进入 electron-builder。
7. 在干净 Windows 测试机运行产物，再进行安装和插件事务验证。

普通新手不必自己修改帧协议或打包验证器。你可以把这一段及第 06 篇的原始日志交给开发人员，要求先完成这项修复，再继续产品定制。

<a id="验收"></a>
## 5. 验收清单

### 5.1 本地开发验收

- [ ] 固定版本的 Node/pnpm 检查通过。
- [ ] 根目录依赖安装成功，当前工作区链接有效。
- [ ] 完整源码构建成功。
- [ ] Electron 窗口实际打开，而非只出现 `Build complete`。
- [ ] Host ready，聊天界面和插件资源正常。
- [ ] 模型能返回一次无副作用的简单回复。
- [ ] 会话在重启后仍可访问。
- [ ] Windows 退出应用后，其 Host 子进程结束。

### 5.2 测试安装包验收

- [ ] 打包命令退出码为 0，目标目录有新产物。
- [ ] 原生模块与 Host smoke 均通过。
- [ ] 干净机器不装系统 Node/pnpm 也可运行核心程序。
- [ ] 安装路径可选，中文和含空格路径经过实际测试。
- [ ] 本机目录选择器正常，取消选择不会卡住界面。
- [ ] 插件安装、启停、卸载、失败恢复有实际结果。
- [ ] 应用安装目录与用户数据目录归属清楚。
- [ ] 只分发完整目录或安装器，不分发缺资源的裸 `.exe`。

### 5.3 企业正式发行验收

- [ ] 应用名、图标、UI 标题、App ID 和更新域名一致。
- [ ] 安装器具有预期签名，更新来自企业控制的发布渠道。
- [ ] 旧版本升级后会话和配置符合保留策略。
- [ ] 插件 peer 版本及原生运行时变化经过验证。
- [ ] 两个账户不能通过历史接口、事件流、缓存或文件访问互相越权。
- [ ] 智能体使用授权、RAG 文档授权和微应用写权限均在服务端落实。
- [ ] 错误日志不主动泄露密钥，退出登录会清理应清理的本地认证状态。
