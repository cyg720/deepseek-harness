# 审批、提问与异步生命周期

## 摘要

审批和提问是 Host 等待中的请求，不是独立前端表单。官方 domain 持有请求，qs 卡片负责展示和调用既有回答能力。切换会话、切换界面、卸载插件和 Host 撤销必须分别处理。

## 所有权与数据路径

```text
Host scoped waterfall → Remote Event → 官方 UI listener
  → PendingApproval / PendingQuestion
  → uiSession pending domain → root useSessionPendingInteraction
  → qs 宿主按 SessionId 取请求 → chain select → 卡片
  → pending.answer → 原 listener 返回结果 → Host 继续
```

官方 pending 对象是当前交互协议特定的可回答 carrier。它的存在不意味着可以把任何 service 对象任意注入组件。qs 以类型引用其接口，不能运行值导入另一个 feature 插件的类来做 instanceof；跨包选择使用实际 discriminator，并覆盖当前支持的 kind。

不要重新监听同一个 Host 事件并再创建另一份 pending，除非正式设计明确替换请求所有者。双 listener 可能改变 waterfall 顺序与处理者。只重写卡片时保留官方 domain 和请求存续。

## 审批协议

PendingApproval.kind 为 approval。交互允许的回答是 `allowed-once` 或 `rejected`；不要发明 always-allow 字符串或把关闭卡片当作拒绝。answer 返回 Promise，但对象只能 settle 一次，再次回答会失败，因此按钮禁用、操作归属和错误恢复都要实现。

request 中可用 toolName、可选 callId、reason 和 signal。最小审批详情可按 callId 关联现有数据；无法关联时显示明确的缺失说明。不得从工具名臆测路径、影响或权限，也不能把“不可获取详情”显示成已验证安全。

官方 `conversation.approval.detail` 是官方审批 entry 声明的子槽，qs 卡片不是其父 owner，不能仅凭槽名直接渲染。应使用本方合法声明的槽或独立数据投影，并保留通用文本兜底。

## 用户提问与 plan-review

PendingQuestion 的 kind 是 `question | plan-review`。只匹配 question 会遗漏计划审核。plan-review 的批准选项由 intent.approve 指定的 label 匹配，不是永远第一项；只有批准项也可以合法显示单按钮。

官方 planReviewOf 只在单问题、存在 detail、非多选、至多两个选项且包含指定批准标签等条件下转换；不符合就保留通用问题表单。请求的全部合法答案必须仍可表达，不能为了双按钮视觉删除第三项或多选能力。

回答使用真实 QuestionAnswer/AskUserQuestionAnswer 类型：保留问题 id、selected 中的原始 option label，以及存在时的 custom。自由文本不是伪造一个名为 Other 的服务端选项。按实际 schema 校验空回答、多选、混合文本和整批答案；不能因为按钮变可点就判定协议正确。

用户、模型提供的 label 和问题正文属于数据，按原值回传；本地化只作用于界面自己的“提交”“失败”等文案。内部判断不能根据翻译后的批准/拒绝按钮文字决定语义。

官方对象有 cancel/delegate/abort 等不同动作，不意味着 qs 产品必须暴露全部按钮。第一优先计划不提供提问跳过/取消，是范围选择；不能为套原型而自动调用 cancel。

## 生命周期矩阵

| 场景 | 请求处理 | 视图与草稿 |
|---|---|---|
| 切会话 | 不 answer、不 abort | 按 sessionId + pending.key 存表单；返回从真实快照重建 |
| 奇术切官方 | 保留官方请求 owner | 当前界面呈现并回答；不能双方自动回答 |
| 仅 qs 卡片卸载/HMR | 不结束官方请求 | qs 状态能否保留取决于 store 生命周期，须明确 |
| 官方 domain 真正卸载 | 按 registerPendingInteraction 的释放协议委托并等待完成 | 不能承诺请求继续由已经卸载的 owner 持有 |
| Host signal abort | 结束请求，移除卡片 | 不标记“用户拒绝”或“提交成功” |
| answer 已发起但视图离开 | 结算原请求 | 不写到新会话，不重开旧卡片，不忽略原忙碌状态清理 |
| answer 失败 | 根据当前请求是否仍有效恢复动作 | 不能把已撤销的旧请求重新变成可提交 |
| 已当选 chain 卡片崩溃 | 不自动改选下一卡片 | 显示错误/重试，不能让 composer 永久无解释地禁用 |

## 必须覆盖的测试

1. 审批允许一次、拒绝、重复点击、Host 撤销、缺详情、详情数据不可信。
2. 一批多问题、单选、多选、无选项自由回答、多选加 custom、部分未答。
3. plan-review 批准项在第二位、只有批准项、不符合专门布局时退回通用表单。
4. 回答过程中 A→B→A、切官方再返回、qs HMR、官方 owner 卸载；分别证明正确生命周期。
5. 真实 chain owner props 正确命中，错误面不会误判为请求已处理。
6. 同 session 不同 pending.key 的草稿和提交锁隔离，旧回调不能清新请求草稿。

## 开发备注

“请求还在”与“用户答案已成功返回 Host”需要不同证据；局部 Promise resolve、按钮消失或 React 卸载都不能单独证明模型已继续。
