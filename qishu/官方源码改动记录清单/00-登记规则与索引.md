## 登记范围

官方文件指从 DeepSeek Harness 上游继承的文件，包括业务源码、公共接口、配置、依赖清单、锁文件、构建与检查脚本、测试、快照、生成文档、协作规则，以及这些文件的移动或删除。已经被奇术修改过的官方文件，再次修改仍须登记。是否属于官方文件依据文件来源判断，不能仅依据路径判断。

本目录只记录继承自官方的文件改动。二开自有文件无论存放在 packages/qs、qishu 或官方目录内的 qs 子目录，均不在本目录登记；其新增、修改、迁移、删除及差异快照也不纳入。如果二开功能引起官方装配、测试配置或生成文件变化，仅登记受影响的官方原文件。

仅同步官方上游版本的批次可单独记录上游提交范围和完整文件差异清单，明确哪些本地定制发生了冲突及其处理结果。不能把上游批量更新误计为奇术功能改造。

## 二开文件隔离规则

二开文件仍按根 AGENTS.md 使用 qs 子目录隔离，隔离规则不意味着纳入本目录。官方文件来源决定登记范围；官方文件的必要原位修改须说明原因，不能通过移动或复制到 qs 来规避登记。

## 登记与维护流程

1. 修改前核实文件来源；仅对官方原文件登记准确路径、目的及必要原位修改原因。二开自有文件不登记。
2. 修改后核对实际差异，将真实发生的文件变更更新为“工作区已改”或“已提交”，补充影响、验证结果和未验证事项。未实施的条目保留“计划修改”或明确取消。
3. 提交前逐项核对暂存区文件与记录，覆盖官方生成文件、删除、重命名及已有测试修改；记录中的命令及结果必须来自实际执行。
4. 每一批后续修改追加批次记录，并同步更新[官方源码改动总表](总览-官方源码改动列表.md)和逐文件差异快照；逐个列出官方中文、配对文件及已有快照，按路径排序。同一文件的不同修改目的分别记录，不抹去已有批次。回退需新增回退记录，并说明残留接入和依赖处理。
5. 提交前尚无提交号时写“待提交”；提交后可在后续登记时补记可核验提交号，不为填入自指提交号反复修改提交。

本要求是仓库协作规则，目前没有新增自动阻断提交的检查脚本。记录齐全不代表代码验证通过，已提交也不代表已验收。

## 记录字段

| 字段 | 必填内容 |
|---|---|
| 批次与日期 | 唯一批次标识、日期、工作分支和核对基线 |
| 文件与操作 | 仓库相对路径、源码链接；修改、生成更新、移动或删除 |
| 文件来源 | 确认为继承自官方的原文件；二开自有文件不纳入 |
| 目的与范围 | 解决什么问题、改到什么位置、为何需要涉及官方文件 |
| 是否必须改动 | 总表逐项填“是”或“否”；注明保留的功能与检查前提，存在替代方式时说明迁移条件，不将“否”当作可直接撤销 |
| 状态与证据 | 计划修改、工作区已改、已提交、已回退或已取消；可核验提交号或工作区差异 |
| 影响与上游合并 | 运行行为、接口、构建、默认装配、官方 UI 的影响，以及上游更新时应保留的内容 |
| 验证 | 实际运行的检查及结果；未执行的检查明确写待验证 |
| 回退 | 对应移除或恢复动作、关联配置和依赖，不默认整文件恢复覆盖后续工作 |
