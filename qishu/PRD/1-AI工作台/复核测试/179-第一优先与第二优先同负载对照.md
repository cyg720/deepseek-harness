# 第一优先与第二优先同负载对照

日期：2026-09-24。范围仅为历史打开和首次分页，不代表第二优先全部性能要求已验收。

## 隔离与方法

基线为 `906b6de1e2`，在专用 Linux 容器的 `/home/node/review-baseline` 中建立 detached worktree；当前未提交实现位于该容器 `/review`。没有切换或重置主机分支。两边分别冻结锁文件安装、执行完整 `pnpm run build`，均退出 0；基线首次离线安装缺少 tarball，随后保持 frozen-lockfile 联网安装成功，原失败日志保留。

测量代码为 `benchmarks/qs/baseline-comparison.perf.ts`。两边使用同一份脚本与 `qishu/config/vitest.long-history.config.ts`，相同 Chromium 149.0.7827.55、Node v24.21.0、1280×900 视口、Linux 内核及 CPU。先运行基线，再运行当前版本；不同时执行测试、构建或另一组基准。

使用当前 `syntheticHistory` 一次生成 158、1,580、7,900 个完整轮次的合法归档，存于容器 `/home/node/qs-comparison-fixtures`，两边读取同一文件，避免旧生成器忽略新参数。样本逐项输出 SHA-256、字节数和事件数；第一条为预热，另五条用于探索性中位数。每次新建临时 Host 与浏览器并完整关闭，打开测量从点击会话到最后回答可见且经过两次 animation frame；分页测量从点击加载历史到节点数增加并经过两次 animation frame。时间包含 Playwright 操作与等待开销，不是纯渲染 CPU 时间。

## CPU 诊断

浏览器及 Host 的最大档诊断各一条均执行成功；日志 `logs/repair-v1-comparison-profile-before.log`、`logs/repair-v1-comparison-profile-after.log`、`logs/repair-v1-comparison-hostprofile-before.log`、`logs/repair-v1-comparison-hostprofile-after.log`。该四次不是稳定性样本，不用于上表；第一次浏览器基线诊断曾与主机类型检查重叠，更不能用于独立时间预算。

浏览器 profile 中空闲采样分别约 4.08/4.51 秒和 5.44/5.86 秒。Host profile 的主要自耗时在 token-meter 的 contextBreakdown 投影：commitSurfaceTokens 与 apply；调用链分别经过 session-query 的 preparedProjections/hydratePrepared/restore，以及 Agent prepare 的 stateOf/materializeCells/buildCell。两条链在基线和当前版本都出现，不能凭采样时间断言当前调用次数翻倍。

已核对两边 token-meter 与 session-projection 构建文件 SHA-256 分别一致，因此不能把差异直接归因为这两个模块的代码修改。后续需统计投影恢复次数、对应 RPC 和缓存命中，再确定二开是否增加重复读取或同步工作。本轮保留原始 `.cpuprofile` 于忽略的 logs 目录，不盲改官方投影算法；性能问题尚未解决。

## 限制

每档五个有效样本只能支持中位数观察，不输出 p95 或稳定性保证；串行运行仍受宿主机器的其他进程影响。记录初始和分页后实际阅读节点数，持久事件数不等于已加载 DOM 数。本项不覆盖 1k/10k 完整加载节点、连续流式、全部 W 面板资源释放、原生查找和完整原型验收，也不构成回归预算已通过的结论。

当前版本的顶部哨兵可能在点击后自动继续取页，分页后节点数：前两档为 208/313，最大档为 208/312/416，基线均为 208。两边输入文件相同，但该动作完成的渲染工作量不完全相同；分页耗时只能作为各自用户操作观察值，不能直接按相同比例判断退化。打开阶段的初始节点数单独核对，未通过禁用当前功能来伪造等量输出。
