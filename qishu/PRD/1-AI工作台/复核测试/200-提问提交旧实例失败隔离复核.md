## 真实结果交付与插件重载

后续源码核实：官方 PendingQuestion.answer() 同步结算本地 waterfall 并返回 Promise；Host 结果由 Gateway 另行调用 /api/$events/result 发送。不能将卡片方法的 Promise 解释成 Host 持久化确认。测试因此控制实际 Gateway 请求，而不是假造卡片等待远端回执。

interaction-roundtrip.e2e.ts 新增 delivers a held question result once after the QS question plugin reloads：使用官方 question-composer 录制模型、真实请求及插件产物，浏览器回答后暂缓结果送达 Host，确认零 tool/result；发送该 QS 提问插件的 rebuilt 通知并观察旧样式节点释放、新样式挂载；期间没有重建待答卡，输入草稿保留。放行实际请求后，等待权威 turn/end=completed，确认一次结果请求、一次工具结果，完整持久 Session 与官方录制一致。

首次仅等转写包含 DONE，误命中了用户提示词，导致过早关闭及持久回放缺尾部；已改为权威终态等待，未调整快照或生产代码。Windows最终1项通过、26未选中，10.43秒（repair-v1-question-delivery-hmr-final.log）；Linux同场景通过（repair-v1-question-delivery-linux.log）。Host类型及文件lint退出码0。最初失败日志 repair-v1-question-delivery-hmr.log 保留。

## 交付失败后的权威请求恢复

上述浏览器用例扩为 settles held question delivery after QS plugin reload 的 delivered/failed 两种情形。failed 在提问插件重载后中断第一次真实 /api/$events/result 请求；官方连接恢复后重新呈现 Host 仍未结算的请求，断言此时 tool/result 为零。明确重新填写并提交，最终有两次交付尝试但只有一次实际工具结果，输入草稿保留，权威 turn/end 为 completed，持久 Session 完整回放一致。

Windows两项通过、26未选中，17.44秒（repair-v1-question-delivery-recovery.log）；Linux两项通过（repair-v1-question-recovery-linux.log）；Host类型和文件lint通过。此处模拟网络提交前失败，没有模拟 Host 已受理但响应丢失，不能把这两种故障视为同一个验证。审批对应路径仍未关闭，T42仍部分完成。

## 审批对应交付组合

同一时序夹具扩展审批拒绝，覆盖 delivered、failed、ack-lost。Windows 使用录制模型工具名映射到实际 pwsh，Linux 保留实际 bash；不执行被拒绝的写入。每种情况均断言一次 approval/decided 且 outcome=rejected、目标 notes.txt 不存在、输入草稿保留、待答卡消失；失败前未产生工具结果，恢复后明确再次拒绝。审批的拒绝结果与原“允许”录制不同，因此不对该分支伪称原始全日志一致；提问分支继续完整录制比较。
