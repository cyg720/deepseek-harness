# 双后端会话写锁冲突排查

2026-09-18 用户反馈官方界面和奇术工作台不能提问，页面地址为 http://127.0.0.1:3080/，报错涉及 session-d9d0710e-b964-4947-99bb-1fbfb44638cb。本次未修改官方或 QS 产品代码，未删除或重写会话数据。

## 原因与证据

现场同时存在两个 Web 后端：PID 45284 从 2026-09-17 21:29 起监听 8081，命令为 dsh --profile web --no-open --port 8081；PID 49340 从 2026-09-18 16:41 起监听 3080，命令为 dsh web。8080 属于 Docker，与本次 DSH 冲突无关，未处理。

官方 JSONL 存储在 Windows 上使用按会话路径生成的命名信号量保护单写者，句柄随进程存活，不以 HTTP 端口区分。错误中的 gateway/internal 是 API 错误类别，不是持有锁的进程名称。相关实现见 [lease.ts](../../../../packages/session/session-persistence-jsonl/src/lease.ts)、[Windows 锁实现](../../../../packages/session/session-persistence-jsonl/src/win32.ts) 和 [API 会话恢复](../../../../packages/api/session-controller/src/agent.ts)。

对用户指定会话的实际存储路径执行官方锁函数探测，关闭旧后端前返回 EBUSY（Win32 32）；关闭旧后端后，同一路径立即获取成功并释放。这个对照直接证明 8081 旧实例造成该会话的写锁占用，不是据两个端口的存在作推测。

## 处理

关闭前核对旧进程的 PID 与启动命令，确认其没有活动 TCP 连接或直接子进程；只终止旧 PID 45284，保留用户使用的 PID 49340。处理后 3080 仍监听，8081 已停止。目标会话的两个已存在代际文件在关闭前后 SHA-256 一致，探测没有写入会话文件，也没有删除锁文件或放宽单写者约束。

现场 Web 装配配置为 defaultUi: official、showOfficialUiEntry: true，用户可在同一 3080 后端中双向切换界面。使用同一份会话数据时应复用一个后端；不同端口不能隔离会话写锁。若需完全独立的并行实例，应使用不同数据根，但它们不再共享同一会话历史。

已确认目标会话写锁冲突解除。已请用户刷新 3080 并分别复测已有会话继续提问、新建会话发送；尚未收到结果，因此不将存储锁验证表述为两条页面发送流程均已验收。浏览器自动化连接在本次不可用，直接 HTTP API 请求受认证保护，未绕过认证、未代发模型请求。

此前建议通过另一端口另起官方界面时遗漏了共享会话写锁限制；后续应优先使用同一后端的界面切换入口，或停止旧后端后再启动新的界面配置。
