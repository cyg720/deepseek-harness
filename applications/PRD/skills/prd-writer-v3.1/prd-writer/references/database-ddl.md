# 数据库 DDL 交付规范

适用于创建或修订含数据库设计的 PRD。生成 SQL 文件不授权运行 SQL；沿用用户提供的数据库引擎、版本和命名，版本未知时标待核验，不擅自迁移技术栈。

## 正文与文件

第四章必须给出覆盖本模块适用表的完整建表脚本，并将同一段 SQL 保存为 `<module>.schema.sql`。SQL 围栏内不能使用省略号或“其余类似”代替语句。已有库的增量修订另外提供迁移 SQL 与执行顺序，不能把完整建表脚本当作存量升级命令。只消费外部服务且没有数据库对象时写 N/A 和依据。

说明目标引擎/版本、schema、依赖扩展、建表顺序、现状与目标差异、方案状态和关联 DB/Q。输入 DDL 有错误时保留原始资料，在交付草案中修正确定的语法错误并记录差异；不能仅交付错误清单。影响业务的未知项给出明确标注的候选方案与假设，关联阻断 Q；无法选择时分列互斥 SQL 方案，不能把其中一个冒充已批准设计。

## 完整性

- 每张表有完整 `CREATE TABLE`，包含主键、字段类型/长度、可空性、默认值、适用唯一约束、外键及删除/更新行为、检查约束；按数据库能力处理序列、身份列、时间和 JSON。
- 表和每个列都提供数据库可存储的注释，说明业务含义、枚举、单位、时区、敏感性或来源等适用语义。PostgreSQL 用 `COMMENT ON TABLE/COLUMN`，MySQL 用表/列 `COMMENT`；引擎不支持时用紧邻 SQL 注释说明限制。
- 完整列出普通、唯一、复合及适用条件索引的实际语句。索引表记录名称、表、列顺序/条件、关联 API 查询或约束、维护代价。主键/唯一约束已隐式建索引时写明，不重复创建等价索引；无额外索引时说明查询依据。
- 核对组合唯一性和租户范围、JSON 引用的保障方式、分区键与唯一键限制、外键依赖、软删除、updated_at 维护方式。原资料没有的关系/状态列必须标目标建议，不能宣称现有库已支持。

## 校验、测试数据与验收

正文 SQL 与附带文件逐字核对；静态检查表/列注释覆盖、重复对象名、引用顺序、索引对象存在、类型及约束与字段表一致。新建库、迁移、非法值/重复值/悬空引用拒绝、索引计划检查及恢复分别关联 TC、TD、AC。数据生成器按相同字段与约束生成，故意非法数据单列；说明生成 ID 与实际主键映射和序列处理。

未获授权不得连接或修改数据库。未实际执行时写“静态检查完成，数据库执行未验证”，注明仍需在批准隔离环境执行的初始化/迁移/约束/查询计划验证；不能声称 SQL 已运行或可直接投产。恢复方案不得以无条件删库或清空业务表作为默认命令。
