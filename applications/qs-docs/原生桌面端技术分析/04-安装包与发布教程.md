# 04 安装包与发布教程

## 摘要

新手先使用 `package:desktop:win:x64:unsigned` 制作本地测试安装包。这条路径不需要 EV 证书和更新服务器。正式分发再增加签名、更新托管与升级验证。

**本次实测提醒：当前检出版本在 `prepare:dsh` 的原生载荷检查阶段报 `Cannot find module 'fs-ext'`，未生成 Windows 安装器。** 下文说明完整命令和成功后的操作；在当前快照上需先按第 05 篇处理该检查与生产依赖不一致的问题，不能把继续等待或重复执行当成修复。

<a id="类型"></a>
## 1. 四类命令的区别

| 目标 | 命令 | 结果 |
|---|---|---|
| 打开开发窗口 | `pnpm run dev:desktop` | 运行源码构建产物，无安装器 |
| 生成 Windows 测试安装器 | `pnpm run package:desktop:win:x64:unsigned` | 未签名、无更新配置的测试产物 |
| 生成正式 Windows 安装器 | `pnpm run package:desktop:win:x64` | 要求发布身份、签名和更新配置 |
| 只准备运行时材料 | `pnpm run prepare:desktop` | 停在准备阶段，不调用安装器构建 |

`prepare:desktop` 不是打包前必须先跑的一步。`package:desktop*` 会自行完整准备；先 prepare 再 package 会重复工作。新手最容易选错的是把 `package:desktop:win:x64:dir` 当作免签名命令；`:dir` 只表示目录产物，它不会自动关闭签名要求。

<a id="未签名"></a>
## 2. Windows 未签名包逐步制作

### 步骤 1：确认前置条件

完成第 02 篇的 Node、pnpm、Python、C++ 工具链准备。确认使用 Windows x64、源码与锁文件一致，关闭会占用当前产物的桌面测试程序。在当前快照上，先解决上方提示的 `fs-ext` 检查阻塞。

### 步骤 2：进入仓库根目录

```powershell
Set-Location 'D:\code\CYG\Github\deepseek-harness'
```

### 步骤 3：设置测试产品标识

```powershell
$env:DSH_DESKTOP_APP_ID = 'com.example.qsdesktop'
```

标识必须满足反向域名格式。测试时可以使用该示例；正式产品换成企业自己的长期标识。此变量只在当前 PowerShell 及其子进程有效，所以设置和打包命令应在同一个终端执行。

不需要设置 `DOWNLOAD_TEST_ORIGIN`，也不需要为此命令设置 Windows 签名变量。未签名入口会清理签名凭据，并且不给最终应用生成自动更新配置。

### 步骤 4：执行完整打包

```powershell
pnpm run package:desktop:win:x64:unsigned
```

首次需要准备生产依赖和运行时，耗时与网络、磁盘和缓存有关。本报告没有测得“成功安装器耗时”，因此不承诺固定分钟数。看到包数量增长和日志持续推进通常说明仍在执行；最终成功必须同时满足退出码为 0 且存在目标产物。

建议需要留证时执行下列等价的日志保存形式，不要同时运行两条打包任务：

```powershell
pnpm run package:desktop:win:x64:unsigned *> desktop-package.log
```

另开终端查看：

```powershell
Get-Content .\desktop-package.log -Tail 80
```

### 步骤 5：定位安装器

成功后，当前代码规定的未签名输出目录是：

```text
D:\code\CYG\Github\deepseek-harness\apps\desktop\.desktop-build\targets\win-x64\unsigned-artifacts
```

列出顶层安装器候选：

```powershell
Get-ChildItem '.\apps\desktop\.desktop-build\targets\win-x64\unsigned-artifacts' -Filter '*.exe'
```

文件名由 `artifactName`、版本、系统和架构展开。不要从更深层目录里随便找到一个 `node.exe` 就当成安装器。此处描述的是成功后的路径，本次没有产生可交付的安装器。

### 步骤 6：在测试电脑安装

把生成的安装器复制到测试电脑，双击打开，按向导选择安装目录并完成安装。配置使用 NSIS，`oneClick: false` 且允许修改安装目录，因此不是仅支持一键无交互安装。[当前 builder 配置](/D:/code/CYG/Github/deepseek-harness/apps/desktop/electron-builder.config.mjs)、[NSIS 官方配置参考](https://www.electron.build/nsis/)。

未签名包可能触发操作系统或企业终端防护的未知发布者提示。仅在确认这是自己的构建产物并符合测试环境要求时继续；不要为了安装测试包关闭全局系统防护。正式对外分发应采用签名路径。

### 步骤 7：验证最终用户不需要系统 Node/pnpm

最好在未安装开发工具的干净 Windows x64 测试机上验证。程序应从安装目录的资源中使用 Node 和 pnpm，而不是碰巧调用开发者电脑 PATH 中的运行时。

核心程序可以从本地完整资源启动；模型调用、远程数据和新增插件仍可能需要网络。不能把“首次不安装核心 npm 包”理解成“整套 AI 功能完全离线”。

额外安装包含原生构建步骤的插件时，还可能需要对应的编译条件和 `allowBuilds` 审查。“核心程序自带运行时”不承诺每一种第三方插件都能在没有开发工具的电脑上安装。

### 步骤 8：检查数据与卸载行为

确认会话保存于实际 Harness home，而不是应用安装目录。安装路径可变不应导致会话路径随意变化。测试创建会话、退出、重启恢复，再测试覆盖升级和卸载。卸载是否保留你需要的用户数据应通过安装器实测确认，本报告不推断未执行的卸载行为。

<a id="流水线"></a>
## 3. 打包脚本内部做什么

了解阶段名称后，就能看出错误发生在“下载”“编译”“组装”还是“安装器”。入口是 [package-target.ts](/D:/code/CYG/Github/deepseek-harness/apps/desktop/scripts/package-target.ts)。

| 顺序 | 阶段 | 结果与检查 |
|---|---|---|
| 1 | 解析 `win-x64` 和 `--unsigned` | 拒绝不支持的宿主/目标组合 |
| 2 | `build:official` | 编译所有需要的 Host、Client、Web、桌面产物并记录官方客户端构建信息 |
| 3 | 打包 dsh、私有 Host 和 vendored 包族 | 本地 npm tarball，避免把源码工作区链接直接分发给用户 |
| 4 | 打包 native/system 入口 | 准备与生产依赖对应的原生能力入口包 |
| 5 | `prepare:runtime` | 下载固定 Node，验证 SHA-256，准备固定 pnpm 并记录版本 |
| 6 | `prepare:packages` | 形成核心生产包集合与清单 |
| 7 | `prepare:dsh` | 在构建阶段安装生产依赖、实体化文件、过滤非运行文件、写运行时清单 |
| 8 | 原生载荷 smoke 与 Host smoke | 在捆绑 Node 下检查原生依赖，并验证后端可启动和提供首页 |
| 9 | electron-builder | 把 Electron 壳和 extraResources 组装为 Windows 安装器 |
| 10 | 发布完成记录 | 正式安装包在全部流程成功后生成；未签名包不生成此记录 |

本次已经到达第 8 阶段的原生载荷检查，并因缺少 `fs-ext` 退出；没有到达安装器生成。这也说明单元测试通过不能代替打包后的原生检查。

### 3.1 程序资源布局

```text
安装后的程序目录
├─ 桌面程序.exe 与 Electron 的运行文件
└─ resources
   ├─ app.asar                Electron 壳的 JavaScript 与壳页面
   ├─ runtime
   │  ├─ node/node.exe        上游 Node.js
   │  └─ pnpm/...             桌面自带的 pnpm
   └─ dsh
      ├─ package.json
      ├─ desktop-runtime.json
      └─ node_modules/...     完整的 Harness 生产依赖
```

这是源码定义的布局示意，不是本次成功安装后取得的目录截图。`asar` 主要封装壳文件，不意味着整个程序只有一个文件；原生依赖和 Host 生产树作为独立资源保留。

### 3.2 为什么安装包和解压后的大小不同

安装器压缩了资源，安装目录保留运行所需的实际文件。当前文件筛选会去掉类型声明、已识别的 source map、构建缓存及部分编译中间文件，同时保留运行 JavaScript、原生模块、DLL/EXE、WASM、许可证和必要资源。[文件筛选策略](/D:/code/CYG/Github/deepseek-harness/apps/desktop/scripts/runtime-file-policy.ts)。

不要通过删除“看起来很大”的 `node_modules` 或 DLL 来瘦身。任何裁剪都需要在最终打包资源中验证实际能力。

<a id="目录包"></a>
## 4. 用未打安装器的目录测试

`:dir` 命令生成可运行的程序目录，便于调试捆绑 Node、插件事务和生产依赖。正式目录命令仍然要求对应的签名/更新配置。

当前参数解析器支持同时指定 `--dir` 与 `--unsigned`。在 Windows x64 上，可以通过已有包脚本传入额外参数：

```powershell
pnpm --dir apps/desktop run package:win:x64:unsigned --dir
```

这是根据 `package.json` 和参数解析代码确认的组合用法，本次未实际生成目录产物。它与安装器命令一样需要先通过 `prepare:dsh`，不能绕开本次 `fs-ext` 阻塞。

分发目录产物时要复制整个程序目录；单独复制里面的应用 `.exe` 通常缺少运行资源。目录包也不代替安装路径、覆盖升级、快捷方式和卸载测试。

<a id="签名"></a>
## 5. 正式 Windows 签名

这一部分由掌握发布证书和签名设备的发布负责人执行，本次没有签名。当前仓库的 Windows 发布实现是针对 GlobalSign EV 公钥证书、SafeNet Token 和指定 SignTool 的方案，不是仅填一个通用 `CSC_LINK` 就可覆盖所有证书类型。

### 步骤 1：准备受控签名环境

准备与私钥匹配的公开 `.cer` 文件、经过验证的 SignTool、SafeNet 私钥容器、已插入并解锁的 USB Token，以及临时注入的 Token PIN。私钥留在硬件设备中。

### 步骤 2：配置应用和测试更新环境

```powershell
$env:DSH_DESKTOP_APP_ID = 'com.example.qsdesktop'
$env:DSH_DESKTOP_AUTO_UPDATE_ENV = 'test'
$env:DOWNLOAD_TEST_ORIGIN = 'https://updates.example.com'
```

域名需替换成企业自己提供的 HTTPS origin，不能附带子路径、查询参数或用户名密码。仅打包不要求 COS 上传凭据，但要求正式打包使用的更新配置有效。

### 步骤 3：配置签名输入并打包

下面前三项是路径/标识示例；PIN 应由你的受控发布环境临时注入 `DSH_DESKTOP_WINDOWS_TOKEN_PIN`，不要把真实 PIN 写入命令历史、源码或 `.env`。

```powershell
$env:DSH_DESKTOP_WINDOWS_CER_FILE = 'C:\release-secrets\company.cer'
$env:DSH_DESKTOP_WINDOWS_SIGNTOOL = 'C:\release-tools\signtool.exe'
$env:DSH_DESKTOP_WINDOWS_KEY_CONTAINER = '替换为实际容器名'
pnpm run package:desktop:win:x64
```

签名输入、硬件或时间戳服务失败时，正式命令会失败，不会悄悄退化为未签名包。脚本还会限制 PIN 中会破坏 SafeNet/CMD 参数的字符。具体限制和隔离方式应以 [Windows 签名脚本](/D:/code/CYG/Github/deepseek-harness/apps/desktop/scripts/windows-sign.mjs) 与 [仓库发布说明](/D:/code/CYG/Github/deepseek-harness/apps/desktop/README.zh.md) 为准。

### 步骤 4：检查签名并进行安装验收

在测试机查看文件“属性 → 数字签名”，核对发布者；测试安装、启动、旧版本覆盖、原生模块运行和异常恢复。需要发布资格验证时，再按仓库说明运行 `smoke-windows.ps1`，其参数必须是实际构建工具路径，不能照抄占位符。

<a id="更新"></a>
## 6. 自动更新和上传

### 6.1 更新是整套产品更新

打包程序在打开主窗口后约 10 秒进行检查，也有手动菜单入口。默认不自动下载和退出安装：有新版本时由用户确认，然后下载、停止 Host、安装并重启。未签名测试包不携带更新配置，所以不能用于证明正式更新链路。[更新控制器](/D:/code/CYG/Github/deepseek-harness/apps/desktop/src/update-coordinator.ts)。

### 6.2 当前更新地址策略

| 模式 | 公共地址 | 企业定制注意点 |
|---|---|---|
| `test` 或未设置 | `DOWNLOAD_TEST_ORIGIN` | 可以指定自己的 HTTPS origin |
| `production` | 固定 `https://download.deepseek.com` | 企业正式版必须调整自有发行策略，不能当成公司更新服务器 |

地址后面追加 `_/harness/desktop/stable/<target>/`。目录名称中的 `stable` 与实际版本 channel 文件不是同一概念：正式语义版本使用 `latest.yml`，当前 `0.1.5-rc.2` 这类版本对应 `rc.yml`；macOS 带 `-mac` 后缀。不要把所有产物都手工改名为 `latest.yml`。

### 6.3 上传由独立命令执行

打包时固定 `--publish never`，不会自动上传安装包。现有上传脚本面向 Tencent COS；不同环境使用各自 bucket 与 SecretId/SecretKey。企业不使用 COS 时，需要提供自己的上传实现，并保留产物版本、大小、摘要和完成记录校验。

配置完整且有明确发布授权后，发布负责人可使用 `upload:win:x64`、`upload:mac:arm64` 或 `upload:mac:x64`。本报告没有运行上传命令，也没有向上游或企业云存储写入任何产物。

上传前需要成功构建完成记录，并核对版本、平台、架构、公共地址和文件摘要。脚本先上传版本化产物，最后上传 channel 元数据；不删除历史版本。未签名测试包没有完成记录，不能冒充正式 release 上传。

<a id="macos"></a>
## 7. macOS 如何操作

Windows 电脑不能直接执行当前 macOS 发布流程。代码要求在 macOS 上运行并验证其原生运行时。

| 目标 | 构建机器 | 命令 |
|---|---|---|
| macOS arm64 | Apple Silicon Mac | `pnpm run package:desktop:mac:arm64` |
| macOS x64 | Intel Mac，或安装 Rosetta 的 Apple Silicon Mac | `pnpm run package:desktop:mac:x64` |

### macOS 操作步骤

1. 在对应 Mac 上准备仓库、Node、pnpm 和原生构建工具。
2. 先按桌面 README 验证开发构建。
3. 设置 `DSH_DESKTOP_APP_ID`。
4. 设置 `DSH_DESKTOP_MACOS_SIGNING_IDENTITY`，值为证书限定名，不带 `Developer ID Application:` 前缀。
5. 设置 `DSH_DESKTOP_MACOS_TEAM_ID`，为 10 位大写字母或数字的 Apple Team ID。
6. 配置一套完整公证凭据，例如 `APPLE_API_KEY`、`APPLE_API_KEY_ID`、`APPLE_API_ISSUER`。
7. 配置自己的测试更新 origin，执行对应目标命令。
8. 等待 App/ZIP 与 DMG 两条产物处理路径均成功，再查看目标目录和发布完成记录。
9. 在实际目标架构的 Mac 上验证签名、公证、首次打开和升级。

API Key 策略的占位示例，适用于 macOS 终端，不是 PowerShell：

```sh
export DSH_DESKTOP_APP_ID='com.example.qsdesktop'
export DSH_DESKTOP_MACOS_SIGNING_IDENTITY='Company Name (TEAMID1234)'
export DSH_DESKTOP_MACOS_TEAM_ID='TEAMID1234'
export APPLE_API_KEY='/absolute/path/AuthKey.p8'
export APPLE_API_KEY_ID='实际KeyID'
export APPLE_API_ISSUER='实际IssuerUUID'
export DOWNLOAD_TEST_ORIGIN='https://updates.example.com'
pnpm run package:desktop:mac:arm64
```

所有凭据示例需由发布负责人替换。当前 macOS 目录包也要求公证凭据；没有与 Windows 相同的受支持 `:unsigned` 快捷路径。Linux 也没有当前受支持的正式桌面目标命令。

<a id="交付"></a>
## 8. 交付与验收

正式给同事使用之前，至少交付安装包、版本说明、实际签名主体、支持的平台、数据目录说明、模型配置方式及故障日志收集方法。若分发目录版，明确要求完整复制目录。

验收必须包含：干净机器启动、无系统 Node/pnpm 启动、模型回复、会话重启恢复、原生目录选择、插件安装失败恢复、旧版升级、应用退出后的子进程回收。企业版还需要独立的账号与数据权限测试，安装器成功不代表这些业务能力已通过验证。

## Dev Note

签名、公证、云上传、另一台电脑安装和实际升级均未在本次报告任务中执行。所有正式发布命令是源码与官方说明核对后的操作指引，不是成功发布证明。
